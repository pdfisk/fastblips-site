Crumb UI Widgets
================

This document describes the widget classes used to build the Crumb user
interface. All widgets derive from a common Widget base, and are arranged in
a tree whose root is the single Viewport.

Widget (abstract)
-----------------
The abstract base class of every UI element. Widget is never instantiated
directly; only its concrete subclasses are.

  - Owns a DOM element and knows its parent widget (null for the Viewport).
  - Has a position and size, set by its parent during layout.
  - Can be shown or hidden; a hidden widget takes no space.
  - Provides layout() to size and position itself, and dispose() to remove
    itself and release any event listeners.
  - id is a name to find the widget by ('' by default; not the element's
    DOM id). childWidgets lists the widgets directly inside it (a Panel's
    children; a Window adds its ButtonBar), and descendants() walks all of
    them, depth first.
  - findById(id) returns the first widget inside this one with that id, or
    null. findByClass(cls) returns every widget inside it of a class: a
    constructor (subclasses match too), or a program class name such as
    'Button' (matched against programClass, which program widgets carry;
    class names cannot be matched by constructor name because the bundle
    is minified).


Viewport (singleton)
--------------------
The outermost container. It fills the whole browser window and is the root
of the widget tree.

  - Exactly one instance exists; obtain it with Viewport.instance. Calling
    the constructor a second time is an error.
  - Holds an optional Navbar docked at the top, an optional StatusBar docked
    at the bottom, and one content widget that fills the space between.
  - Hosts Windows, which float above the content area. The Viewport keeps
    their stacking order and brings a window to the front when it is
    clicked.
  - content is the widget filling the space between the Navbar and the
    StatusBar (or null); Windows float above it. Any widget with a height
    can be docked as the StatusBar (the ?app= page docks a ButtonBar).
  - Listens for browser resize events and lays out the whole tree again.
  - windows returns the open Windows, back to front.
  - visibleWindows and minimizedWindows return the Windows that are
    showing, and those that are minimized.
  - arrangeWindows() cascades the showing Windows diagonally from the top
    left, each sized to 35% of the Viewport's width and height and offset
    30px from the one behind it, front-most last and on top; minimizeAll(),
    restoreAll() (un-minimize and un-maximize) and closeAll() act on every
    Window. The playground's Windows menu offers all four above its list
    of windows.


Panel (abstract)
----------------
A widget that contains other widgets. Panel is never instantiated directly;
subclasses decide how the children are arranged.

  - add(child), remove(child), and a read-only children list.
  - Adding a child sets the child's parent; a widget can belong to only one
    panel at a time.
  - Subclasses implement layout() to place their children, then ask each
    child to lay itself out.
  - Optional padding around the children and spacing between them.
  - Every widget has a box, from the outside in: a margin (clear space
    inside the area its parent gives it), a border (borderWidth pixels, in
    borderColor, or the widget's colour when none is set) and padding
    (between the border and the contents). All are whole pixels, 0 or more,
    and can differ by side: setMargin(n) sets all four sides, and
    setMarginSides(top, right, bottom, left) sets each (likewise padding and
    border width). getMargin() and the like read the top side. A saved design
    holds one number when the sides are alike, else [top, right, bottom, left].
    A row or column counts a child's margin in the space it asks for, and
    keeps its own children inside its border and padding. A Panel's
    children are placed by box, inside its border; padding is drawn by
    Labels and Buttons and used by rows and columns (other classes ignore it).
    A Window has no box.


HPanel and VPanel
-----------------
(src/ui/widgets/hpanel.js, vpanel.js)
Panels that arrange their children in a single row or column.

  - HPanel places children left to right; VPanel places them top to bottom.
  - Each child has either a fixed size or a flex weight along the main axis.
    Fixed-size children are placed first, and the remaining space is shared
    among flex children in proportion to their weights.
  - On the cross axis, children stretch to fill the panel by default.
  - Nesting HPanels and VPanels builds grid-like layouts.


Composite, Stack and the layouts
--------------------------------
(src/ui/widgets/composite.js, stack.js; src/ui/layouts/)
Modelled on qooxdoo's containers (qx.ui.container.Composite and Stack) and
layout managers (qx.ui.layout). Not to be confused with a saved composite
(a widget kept by name in the database): the class Composite is a container.

Composite is a Panel whose children are placed by a layout manager.
  - composite.layoutManager is the layout: set it from a name ('hbox') or a
    Layout; layoutName reads the name. The default is 'basic'. Changing the
    layout places the children again and drops the old layout's settings.
  - A layout works out a box for each visible child and calls
    child.setBounds(...). The box includes the child's margin. Positions are
    inside the Composite's border and padding, so padding is the space
    between the Composite's edge and the layout's area.
  - A child's size comes from, in order: the size the program fixed
    (setWidth / setHeight), what the layout says (flex, a stretch, a cell),
    and the size the child asks for (preferredWidth / preferredHeight).

Stack is a Panel that shows one child at a time, each filling the area. The
first child added is showing. select(i), selectNext() and selectPrevious()
(wrapping round) change it and fire select with the index. The Stack sets its
children's visibility (a TabPanel without the tabs); a saved Stack records
which page shows, and its pages are not saved as hidden. Its layout is
'grow'.

The layouts (LAYOUTS in src/ui/layouts/index.js), after qooxdoo's:

  basic   Children sit where their box says (left, top, width, height), or
          fill the area after fill(). The default.
  canvas  Like basic, but a child can instead be placed by its distance from
          the edges and its size: left, top, right, bottom, width, height,
          each a number of pixels or a percentage ('50%'). Two of the three
          on an axis fix both position and size.
  grow    Every child fills the area. (What a Stack uses.)
  hbox    A row. Each child is as wide as, in order: its fixed width; a
  vbox    share of the space left over, by its flex; the width it asks for.
          Across the row it fills the height unless it has an alignment
          (alignY), when it takes the height it asks for and sits at the top,
          middle or bottom. A VBox is the same down a column (alignX across).
          Options: spacing; alignX (hbox) / alignY (vbox): where the group
          sits when there is space left and no child has flex; reversed.
  dock    Children attach to the edges in the order they were added: a north
          or south child takes the full width left and the height it asks
          for, a west or east child the full height left and its width;
          what remains goes to the center children (the default edge).
          Options: spacingX, spacingY.
  flow    Children side by side, wrapping onto a new line when the next one
          would not fit. Options: spacingX, spacingY, alignX (where each
          line sits), reversed. A child's alignY sits it in its line.
  grid    Rows and columns. A child names its cell (row, column) and how
          many rows and columns it covers (rowSpan, columnSpan). Each track
          is as big as its biggest child unless it has a size; it may have a
          flex, a min and a max. Spare space (or a shortfall) is shared
          among the tracks with flex, within their min and max. A child that
          spans tracks widens the last one it covers that has no size. A
          child fills its cell unless it has an alignment. Options:
          spacingX, spacingY, and per column / row: flex, size, min, max.

Left out: qooxdoo's Atom layout (an icon and a label), as the toolkit has no
icons.

A child's own settings in its parent's layout are child.layoutProps:
{ edge, row, column, rowSpan, columnSpan, alignX, alignY, canvas }, where
alignX is left, center or right, alignY is top, middle or bottom, edge is
north, south, west, east or center, and canvas is six lengths (left, top,
right, bottom, width, height; '' for not set). A layout ignores the ones it
has no use for. cleanChildProps() checks them.

A Composite is saved as { class: 'Composite', layout, layoutOptions,
children }: layout is left out when it is 'basic', and layoutOptions holds
only the settings that differ from the layout's defaults (a grid's as
columns / rows: { index: { flex, size, min, max } }). A child's settings are
saved as layoutProps. A saved Stack has selected (the page showing, left out
when 0) and children.


GroupBox, CheckGroupBox and RadioGroupBox
------------------------------------------
(src/ui/widgets/group-box.js)
Modelled on qooxdoo's qx.ui.groupbox. A GroupBox is a Composite in a frame,
under a title; a CheckGroupBox has a check box in the title and a
RadioGroupBox a radio button. A program can make the last two (a plain
GroupBox is the toolkit's base class of both).

  - The children are placed by a layout manager like a Composite's, inside the
    frame and below the title. The default layout is vbox, not basic.
    A layout takes the room the title and frame need from the container's
    frameInsets ([top, right, bottom, left]; inner() in layouts/layout.js
    subtracts it with the padding): the title row is LEGEND_HEIGHT (24) high,
    and the frame is FRAME_WIDTH (1) wide with FRAME_PADDING (6) inside it.
    The box's own padding comes on top of that.
  - text is the title. checked is the state of the check box or radio button.
    A CheckGroupBox starts checked, a RadioGroupBox not. A plain GroupBox has
    no state: reading checked gives false, and setting it is an error.
  - While the box is not checked its content is disabled: the children are
    dimmed (class cr-groupbox-off) and made inert (element.inert), so they take
    neither clicks nor the keyboard. Children added later are inert too; a child
    taken out is usable again. contentEnabled says which.
  - A change of state fires a change event with detail { checked }, whether the
    user or the program made it.
  - Checking a RadioGroupBox unchecks the others in its group, and they fire
    their change events first. The group is the RadioGroupBoxes in the same
    container; with group set to a name it is every RadioGroupBox with that name
    in the same tree of widgets, wherever they are. Unnamed boxes and named boxes
    are never in a group together. Nothing is checked at first, and a program
    can uncheck the one that is (unlike an HTML radio button, which cannot be
    cleared by the user). Checking two before they are in the same tree leaves
    both checked, so check the one to start with after adding them.
  - For a program: CheckGroupBox(text) and RadioGroupBox(text), with the
    container and layout methods of a Composite, setText / getText,
    setChecked / isChecked, onChange (called with the box and whether it is
    checked now) and, for a RadioGroupBox, setGroup / getGroup. They are saved
    with text, checked (when not the class's default), group and layout (when not
    vbox), and the designer offers them like a Composite.


HSplitPanel and VSplitPanel
---------------------------
(src/ui/widgets/hsplit-panel.js, vsplit-panel.js)
Panels with exactly two children separated by a divider the user can drag.
Both share an abstract SplitPanel base.

  - HSplitPanel places its children side by side with a vertical divider;
    VSplitPanel stacks them with a horizontal divider.
  - The divider position is stored as a fraction (0.0 to 1.0) so the split
    keeps its proportions when the panel is resized.
  - Each side can have a minimum size; the divider cannot be dragged past
    it.
  - Fires a change event when the divider moves, so the position can be
    saved and restored.
  - Double-clicking the divider may reset it to its default position.


Window
------
A top-level panel that floats above the Viewport's content.

  - Has a title bar showing a title and minimize, maximize and close
    buttons, and a content area that holds a single child widget.
  - Moved by dragging the title bar; it is kept within the Viewport so the
    title bar can always be reached.
  - Resized by dragging its edges or corners, down to a minimum size.
  - close() removes the window from the Viewport. A close event is fired
    first, and a handler may cancel it (for example, to confirm unsaved
    changes).
  - Clicking anywhere in a window brings it to the front; isFront tells
    whether it is the front-most window.
  - The front-most window that is showing is the active window: it has
    the stronger title bar and shadow, and the others are drawn inactive.
    isActive tells whether a window is the active one.
  - minimize() hides the window; open() restores it. In the playground each
    minimized window gets a button on the StatusBar, and the Windows menu
    restores it too. minimized tells whether it is minimized.
  - maximize() makes the window fill the Viewport between the Navbar and
    the StatusBar, and keeps it fitted when the browser is resized; restore()
    puts it back where it was. toggleMaximize() switches between the two, and
    double-clicking the title bar calls it. A maximized window cannot be
    moved or resized; maximized tells whether it is maximized.
  - Minimizing, restoring, maximizing and un-maximizing fire a windowstate
    event that bubbles up to the Viewport.
  - Has a ButtonBar (window.buttonBar) along its bottom edge, 30px high,
    below the content area. Subclasses add their buttons to it.
  - The resizable option (true by default) can be set to false for a window
    of fixed size: it has no resize edges and no maximize button, and
    cannot be maximized (double-clicking the title bar does nothing).
    arrangeWindows() moves such a window without resizing it.


TextPanel
---------
A Panel that contains a single text area filling its entire area.

  - The text area is created by the panel and always sized to match it; no
    other children can be added.
  - Exposes the text through a text property (get and set), and fires a
    change event when the user edits it.
  - Can be made read-only, e.g. for program output.
  - focus() moves the keyboard focus into the text.
  - Ctrl+Enter (Cmd+Enter on a Mac) fires a submit event.


MonacoPanel
-----------
A TextPanel whose text is edited in a Monaco editor (the editor behind VS
Code), highlighted for a Monaco language id: new MonacoPanel({ text,
language }), e.g. language 'vb' for VB.NET.

  - Monaco is loaded from cdn.jsdelivr.net the first time a MonacoPanel is
    created, and shared by every later one. Until it arrives the panel works
    as a plain TextPanel; the text typed meanwhile carries over into the
    editor. If it cannot be loaded (e.g. offline), the panel stays a plain
    TextPanel.
  - The text and readOnly properties, focus(), append() and the change and
    submit events work the same with or without the editor.
  - ready is a promise that resolves once the editor is up (to the editor,
    or null if Monaco could not be loaded).


GridPanel
---------
A Panel that is filled by a single table: a header row of column names and
one row per record. Like ListPanel, it tracks the selected row by value and
fires a select event; the keyboard moves the selection.

  - new GridPanel({columns: [{label, width?}], rows, emptyText}).
  - Rows are {value, cells, sort?} objects: cells are the text shown, and
    sort (optional) is what the column is sorted by instead of the text.
    emphasis: true shows a row in bold (a topic with unread posts); title
    is a tooltip for the row.
    rows (get and set) keeps the selected row through a refresh.
  - Clicking a column header sorts by that column; clicking it again
    reverses the order. The header stays in view as the rows scroll.
  - Dragging the right edge of a header resizes that column (at least 40px).
    The first drag fixes every column at its current width; any space left
    over stays empty at the right, and if the columns are wider than the
    panel it scrolls sideways. columnWidths gets the widths in pixels and
    setColumnWidth(index, width) sets one.
  - No other children can be added.


ListPanel
---------
A Panel that is filled by a single List element.

  - The List is created by the panel and always sized to match it; no other
    children can be added.
  - Items are added, removed or replaced through the panel, and the List
    scrolls when they do not fit.
  - Tracks the selected item and fires a select event when the user picks
    one (by click or keyboard).
  - Items are {label, value} objects: items (get and set), addItem(item),
    removeItem(index) and replaceItem(index, item). The selection follows
    the item's value, so replacing all the items keeps the same row
    selected. selectedIndex, selectedItem and select(index) give access to
    it; Up, Down, Home and End move it.
  - An optional emptyText is shown when there are no items.
  - An item may also have header: true (a heading between groups of rows,
    never selected and skipped by the keys), icon (a symbol before the
    label), detail (a short text at the right, such as a count), badge:
    true (shows the detail as a highlighted pill) and title (a tooltip).


TabPanel
--------
A Panel showing one of several pages at a time, chosen by a row of tab
labels.

  - new TabPanel({ tabPosition }): the labels run along the 'top' (the
    default) or the 'bottom' edge, in a 24px strip; the page showing fills
    the rest.
  - addTab(label, widget) adds a page and returns the widget. Pages are
    added only this way; add() is an error. The first page added is
    selected.
  - Clicking a label shows its page and hides the others. select(index or
    label) does the same from code, and fires a select event with detail
    {index, label, widget}.
  - labels, selectedIndex, selectedLabel and selectedWidget describe the
    tabs and the page showing. remove(widget) removes a page and its tab.


OutputPanel
-----------
The output side of a ConsoleWindow: a TabPanel with its labels along the
bottom and four pages.

  - Text: a TextPanel (outputPanel.textPanel) that programs print to. It is
    selected at first. It is writeable: the user can type in it and edit
    what was printed; programs print at its end.
  - Board: a BoardPanel (outputPanel.boardPanel).
  - Canvas: a CanvasPanel (outputPanel.canvasPanel).
  - Physics: a PhysicsPanel (outputPanel.physicsPanel): the Physics class's
    world of falling, bouncing shapes.
  - selectedTab is the label of the page showing; selectTab(label) shows
    another.
  - clear() empties the pages: the text, the board, the canvas and the
    physics world's shapes. No other children can be added.


PhysicsPanel
------------
The Physics page of an OutputPanel: the Physics class's world, a box of
shapes that fall under gravity, bounce, spin and push each other (circles,
balls, rectangles, ellipses and regular polygons; see "The Physics" in
docs/crumb-v0.1-spec.md).

  - The world has a size of its own in units (400 by 300 until the program's
    setSize), with (0, 0) at the top left and y down, and is scaled to fit the
    panel, keeping its shape, as the Canvas is. panel.world is the
    PhysicsWorld of physics.js, the engine, which needs no DOM; the panel
    draws it.
  - Until a program makes its Physics the page shows a demo ball: click to kick
    it. startProgram() gives a program a new, empty world; reset() (before
    each run) puts the demo back; clear() (Clear Output) removes the shapes.
  - A click fires a physicsclick event with the x and y of the world.
  - The world moves only while the page is showing: it pauses when the page is
    hidden or the panel leaves the document, and goes on when it is shown. A
    shape that stays still for half a second falls asleep, and when every
    shape is asleep nothing is animated (no frames) until something changes.
  - Composite shapes are bodies of several parts (physics.js: Body, Part). The
    panel draws world.bodies part by part, at each part's world pose, so a
    group looks like its shapes together; labels come from world.parts.
    Animations (moveTo, rotateTo, scaleTo, oscillate) run inside the engine's
    step, so the panel only has to keep drawing while the world is awake.
  - A PhysicsPanel holds only its canvas.


BoardPanel
----------
The Board page of an OutputPanel: a Panel divided into equally sized
rectangular cells, for board games such as checkers, chess and tic-tac-toe.
new BoardPanel({ rows, columns, checkered, squareCells }); a board is 8 by 8
and checkered unless told otherwise.

  - Rows and columns are numbered from 0: row 0 is the top row and column 0
    the left column. A row or column that is not on the board is a
    RangeError.
  - rows and columns give the size; setSize(rows, columns) changes it (1 to
    100 each) and empties the board.
  - The cells fill the panel, so they are rectangles of the panel's shape.
    Set squareCells to keep them square; the board is then centred.
  - checkered colours the cells alternately light and dark, the top-left
    cell light. A board that is not checkered (tic-tac-toe) is all light.
    The colours come from the theme (board-light, board-dark, board-line,
    board-text, board-selected).
  - Each cell holds a short text - a piece, such as "X" or a chess glyph -
    centred in it and sized to the cell: setText(row, column, text) and
    getText(row, column). "" is an empty cell.
  - A cell can have colours of its own, e.g. to show the legal moves:
    setBackground(row, column, color) and setColor(row, column, color) for
    its text, with getBackground and getColor. "" restores the board's.
  - select(row, column) frames one cell as selected and clearSelection()
    none; selected is { row, column } or null. Both fire a select event
    (detail { row, column }, or null).
  - Clicking a cell fires a cellclick event with detail { row, column,
    text }. A click does not select the cell; the listener decides.
  - clear() empties every cell's text and colours and the selection, and
    keeps the size. No widgets can be added.
  - Programs reach a BoardPanel as their Board (New Board() / Board()); see
    "The Board and the Canvas" under Program widgets.


CanvasPanel
-----------
The Canvas page of an OutputPanel: a Panel that shows a drawing - 2D and
simple 3D graphics, for showing data and for games.
new CanvasPanel({ width, height }).

  - The drawing has a size of its own, in units: 400 by 300 unless told
    otherwise (width, height; setSize(width, height), 1 to 4000 each,
    erases it). (0, 0) is the top left, x goes right and y down. The
    drawing is scaled to fit the panel, keeping its shape and centred, so
    coordinates mean the same at any window size. It is kept at two pixels
    to the unit, so it stays sharp when shown larger.
  - Settings: background (what clear() fills with; white), color (what is
    drawn next; black), lineWidth (1) and fontSize (14), in units. Colours
    are any CSS colour. They are not themed: a drawing looks the same in
    every theme.
  - 2D shapes are painted as they are drawn and stay until clear():
    point(x, y); line(x1, y1, x2, y2); rect and fillRect(x, y, width,
    height); circle and fillCircle(x, y, radius); triangle and fillTriangle
    (three points); polygon and fillPolygon(points), each point [x, y];
    text(x, y, text), with (x, y) its top left.
  - 3D shapes: line3d, triangle3d and fillTriangle3d (points x, y, z),
    box3d and fillBox3d(x, y, z, width, height, depth), centred on (x, y,
    z). x is to the right, y up and z toward the viewer. They are kept in a
    list (at most 20000; clear() empties it) and drawn over the 2D drawing,
    farthest first, each time the drawing is shown. Solid ones are shaded by
    how they face a fixed light. A shape that reaches behind the camera is
    not drawn. This is drawing with the 2D canvas, not WebGL: shapes that
    pass through each other are not cut where they cross.
  - The camera: setCamera(x, y, z) puts it somewhere (it starts at 4, 3, 6);
    lookAt(x, y, z) is the point it looks at (the origin); orbit(angle,
    height, distance) puts it on a circle round that point, angle in
    degrees. Because the shapes are kept, moving the camera and showing
    the drawing again gives the new view without drawing them again.
  - autoUpdate (true at first): each change is shown by itself, at the
    browser's next frame. A game turns it off and calls update() when each
    picture is complete, so a half-drawn picture is never seen.
  - Input: a click fires a canvasclick event with detail { x, y }, in
    units, and gives the canvas the keyboard; a key going down fires
    canvaskey with detail { key }. isKeyDown(key) says whether a key is
    held; mouseX and mouseY are where the mouse last was. Keys are named
    in lower case, without "Arrow": "a", "left", "space", "enter"
    (isKeyDown takes any case).
  - reset() puts everything back as new. No widgets can be added.
  - Programs reach a CanvasPanel as their Canvas (New Canvas() /
    Canvas()); see "The Board and the Canvas" under Program widgets.


Navbar (singleton)
------------------
The navigation strip docked along the top of the Viewport. Navbar is a
subclass of HPanel, so its contents are laid out left to right using the
same fixed-size and flex rules.

  - Exactly one instance exists; obtain it with Navbar.instance. Calling
    the constructor a second time is an error.
  - Added to the Viewport (viewport.navbar = Navbar.instance), which docks
    it at the top of the page.
  - Is 35px high and spans the full width of the Viewport. Windows cannot
    be dragged above it.
  - Its children are a title or logo on the left and the navigation items,
    typically Menus; a flex spacer can push items to the right-hand end.
  - Each item has a label and an action; the active item is highlighted.
  - Items that do not fit may collapse into an overflow menu on narrow
    screens.


StatusBar (singleton)
---------------------
The status strip docked along the bottom of the Viewport. StatusBar is a
subclass of HPanel.

  - Exactly one instance exists; obtain it with StatusBar.instance. Calling
    the constructor a second time is an error.
  - Added to the Viewport (viewport.statusBar = StatusBar.instance), which
    docks it at the bottom of the page.
  - Is 24px high and spans the full width of the Viewport. Windows cannot
    be dragged below it.
  - A message Label on the left (message, or show(text, tone) where tone
    'error' shows it in red) and an info Label on the right (info).
  - setTasks([{label, title, action}]) shows a row of buttons between the
    message and the info; the playground uses it for minimized windows.
  - In the playground the consoles report on the message (running, finished,
    stopped, load errors) and the info shows a live summary of the
    scheduler's processes.


Menu
----
A pulldown menu: a labelled button that opens a list of items when clicked.
Menu is a Widget, not a Panel; its items are not widgets.

  - addItem(label, action, { checked, enabled }) adds an item. Choosing the
    item closes the menu and runs action(). If enabled is given, it is
    called each time the menu opens and the item is greyed out and cannot be
    chosen while it returns false.
  - addSubmenu(label, items) adds an item with an arrow that opens a
    submenu beside it (to the right, or to the left if there is no room)
    when pointed at or clicked. items is a function called each time the
    submenu opens, returning items in the itemsProvider shape. Only one
    submenu is open at a time, and choosing an item in it closes the menu.
  - addSeparator() adds a dividing line; an itemsProvider can return
    {separator: true} for the same.
  - If checked is given, it is a function called each time the menu opens;
    a check mark is shown next to the item while it returns true.
  - Only one menu is open at a time. Clicking outside the menu or pressing
    Escape closes it.
  - The list is drawn above all Windows, and kept inside the browser window:
    it opens below the menu's button, or above it when there is no room
    below (as for a menu in a Window's ButtonBar).
  - In a ButtonBar a Menu is drawn like the Buttons beside it, with a small
    down arrow after its label.
  - Setting itemsProvider to a function makes the menu dynamic: the function
    is called each time the menu opens and returns the items to show, in the
    same {label, action, checked, enabled} shape. "(none)" is shown for an
    empty list.


Startup
-------
Crumb.ui.start() picks the UI for the device (isMobileDevice() in
src/ui/device.js): on a phone it calls startMobile(), otherwise
startDesktop(). A ?ui=mobile or ?ui=desktop page parameter overrides the
detection. A phone is a browser that reports itself as mobile, a mobile
user agent, or a touch screen whose short side is under 600px; tablets get
the full UI.

The mobile UI (src/ui/mobile/app.js) is, for now, a single landing page
with the name, a short description, a link to the full version
(?ui=desktop) and the build time. It uses plain DOM and the theme
variables, not the desktop widgets.

When the full UI starts, the Navbar is docked at the top of the Viewport
with, from left to right, a File menu, a Database menu, Basic, Python,
Process and Designer buttons, a Settings menu, and a Windows menu, which is always the
last menu. At the right end is the time the page was built, e.g.
"Built 2026-09-23 13:47:05 UTC". The
StatusBar is docked at the bottom, and the TranscriptWindow is open.

  - The Help menu, after the My Projects and Shared Projects buttons, has Widget
    Documentation, which opens the WidgetHelpWindow.
  - The File menu starts with Sign In, which opens the SignInWindow, and
    Register..., which opens the RegisterWindow, then a separator. It then has New Basic and New Python; then Open..., Save and
    Save As...; then Delete, with a separator between the groups.
    - New Basic and New Python open an empty console in that language.
    - Open... asks for a source file and opens it in a new console: .bas
      files in a BasicConsoleWindow, .py files in a
      PythonConsoleWindow. The console's title shows the file name.
    - Save writes the front-most console's source back to its file; for a
      console with no file yet it does what Save As... does.
    - Save As... asks where to save the front-most console's source.
    - Save and Save As... are greyed out unless the front-most showing
      window is a console.
    - Delete asks for confirmation, then deletes the front-most console's
      file. The source stays in the console, which no longer has a file.
      It is greyed out unless that file was opened or saved through the
      File System Access API (Chrome, Edge), since other browsers give a
      page no way to delete files.
    - Where the browser has the File System Access API (Chrome, Edge), Save
      writes the file in place. Elsewhere Open uses a file chooser and Save
      downloads the file.
  - The Database menu has Basic and Python items, which open the
    BasicDatabaseWindow and PythonDatabaseWindow (or bring them to the
    front).
  - The Basic button opens a new BasicConsoleWindow.
  - The Python button opens a new PythonConsoleWindow.
  - The Process button opens the SchedulerWindow (or brings it to the
    front).
  - The Designer button opens a new DesignerWindow (the GUI designer).
  - The Settings menu has three items that open submenus, each with a check
    mark on the choice in use. Choosing one takes effect at once and is
    remembered for the next visit.
    - Theme: Classic, Apple or Steampunk.
    - Code Font: JetBrains Mono (the default) or IBM Plex Mono, used for
      source, output and lists, and in the Monaco editor. The font is
      fetched from Google Fonts when first chosen; until it arrives, or if
      the page is offline, the theme's own monospace font is used.
    - Database: Remote (https://api.fastblips.com, the
      default) or Local (http://localhost:3000). Open Database windows
      reload from the new server.
  - The Windows menu lists every open window by title, front-most first,
    with a check mark on the front-most one. Choosing a window shows it (if
    hidden) and brings it to the front.
  - The TranscriptWindow is always listed, so choosing it reopens it after
    it has been closed.
  - The My Projects button, after Windows, opens the ProjectsWindow; the Shared Projects button, after it, opens a new CommunityProjectsWindow
    (or brings it to the front).


Button
------
A clickable, labelled Widget.

  - new Button(label, action); clicking it runs action().
  - label and enabled properties.
  - Used on the Navbar and in ButtonBars.


ButtonBar
---------
A row of Buttons along the bottom of a Window. ButtonBar is a subclass of
HPanel.

  - Is 30px high and spans the full width of the Window.
  - addButton(label, action) creates a Button, adds it and returns it.
  - Buttons are left-aligned, in the order they were added.


HSplitWindow
------------
A Window whose content is an HSplitPanel.

  - left and right properties get or set the two sides of the split.
  - Accepts the usual Window options plus left, right and position (the
    fraction of the width given to the left side).


ConsoleWindow
-------------
An HSplitWindow for editing and running code: the shared base of the
language consoles below. Any number of consoles can be open at once.

  - The left side is an editable TextPanel holding the source; the right
    side is an OutputPanel (console.outputPanel) with Text, Board and
    Canvas tabs. console.output is its Text page, which programs print to.
  - Its ButtonBar has, from the left, Run (runs the source), Clear Output
    (empties every page of the OutputPanel) and Clear Input (empties the
    source) buttons. Ctrl+Enter in the source also runs it.
  - After Clear Input comes a Priority menu (console.priorityMenu) with items 1 to 5; the
    chosen one is checked and kept in console.priority (default 3). The
    console's programs run at that priority on the Scheduler (1 highest,
    5 lowest), and choosing one also changes the priority of the program
    running now (setPriority(level)).
  - console.compiled is compiled code that came with the source (a
    record's compiled_code, when opened from a DatabaseWindow). Run and
    Launch use it instead of compiling for as long as the source still
    matches it; see "Compiled code" below.
  - After Priority comes a Launch menu (console.launchMenu), placed like
    the other buttons, with Desktop, Mobile, a separator and Web. They call
    launch('desktop'), launch('mobile') and launch('web'). The first two
    open a new DesktopLaunchWindow or MobileLaunchWindow with a copy of the
    console's source. Web opens the app saved in the database under the
    console's script name as a full page (the ?app= page) in a
    new browser tab; it runs the saved version, not edits made in the
    console, and needs a script that came from the database (console.
    recordName and recordOwner, set when a record is opened in a console):
    otherwise the StatusBar says so. addLaunchItems(menu, launch) in
    launch-window.js builds these items, and launchWeb(name, owner) opens
    the page.
  - A subclass sets its language by overriding the static titlePrefix
    (e.g. 'Basic Console') and defaultText (the starting source), and the
    run() and stop() methods. In ConsoleWindow itself both do nothing.
  - The static spawn(source, { name, output, onExit }) compiles source in
    the console's language and spawns it on the shared Scheduler, printing
    to output (a TextPanel); load errors are written to output instead. It
    returns { process, errorCount } and does not start the scheduler. run()
    and LaunchWindow's Go both use it. In ConsoleWindow it spawns nothing.
  - createInput(text) makes the source pane: a TextPanel unless a subclass
    overrides it (e.g. with a MonacoPanel).
  - Each subclass numbers its own windows: the first is titled with the
    prefix alone, then '<prefix> 2', ... Every new console, of any kind,
    opens slightly below and to the right of the previous one.
  - Closing a console calls stop().


BasicConsoleWindow
------------------
A ConsoleWindow that runs Crumb code, titled Basic Console, Basic Console 2, ...

  - The source pane is a MonacoPanel with VB.NET highlighting.
  - While its program runs, the console's output pane is dimmed a little
    (running is true); it returns to normal when the program ends.
  - Run compiles the source and starts it on the Scheduler shared by all
    consoles (src/ui/runtime.js), so programs run in the background, take
    turns, and a Sleep never freezes the page. Output appears as it is
    printed. Running again, or closing the console, stops its previous
    program.
  - Load and runtime errors are shown in the output, in the section 11
    diagnostic format.
  - Lines written by the Transcript built-in are appended to the
    TranscriptWindow rather than to the console's output.


PythonConsoleWindow
-------------------
A ConsoleWindow for Python code, titled Python Console, Python Console 2, ...

  - Starts with print("Hello, world") as its source.
 

LaunchWindow (abstract)
-----------------------
A Window that runs a console's program as an app. Launch windows are
opened from a console's Launch menu; any number can be open at once.

  - new DesktopLaunchWindow({ source, console }) or
    new MobileLaunchWindow({ source, console }): source is the program and
    console the ConsoleWindow it came from (kept as window.source and
    window.console). The source is a copy taken at launch: editing the
    console afterwards does not change it. The console's class
    (window.language) runs it, so Go still works after the console closes.
  - Titled with the name of the script loaded in the console that launched
    it (console.scriptName): the console's file name, e.g. fizzbuzz.bas;
    for a console opened from a DatabaseWindow, the record's name; otherwise
    the console's title (e.g. Basic Console 2).
  - Each new launch window opens slightly below and to the right of the
    previous one.
  - The content (window.screen) is the app's screen, an AppScreen: a
    TextPanel (window.textPanel) that fills all of it, which the program
    prints to, with the program's widgets (New Button, ...) over it. The
    same in DesktopLaunchWindow and MobileLaunchWindow.
  - Its ButtonBar has Go, Reset and Show source buttons (window.goButton,
    window.resetButton and window.sourceButton), which call go(), reset()
    and showSource(). Show source opens a SourceWindow
    (src/ui/windows/source-window.js) with the source the window runs - the
    copy taken at launch, or for a project one tab per script, in order;
    pressed again it brings that window to the front, and it closes with
    the launch window. In a MobileLaunchWindow the source is instead shown
    on the phone screen, in place of the output (see MobileLaunchWindow).
  - Wherever the source is shown it can be edited (a SourceEditor), and
    there is a Compile button (in the SourceWindow's button bar, or the
    MobileLaunchWindow's while it shows the source). It is enabled only
    while the source differs from the one last compiled (at first, the
    copy taken at launch). compile(editor) compiles the edited source,
    without running it (runner.recompile(texts); for a project only the
    scripts that changed), and every later Go runs that source and its new
    code instead of the compiled code the window was given or this page's
    compile cache; Compile is then disabled until the next edit. Nothing is
    saved to the database or back to the console. A toast says it compiled,
    or how many errors there were and the first; on errors the source and
    code used before are kept and Compile stays enabled (for a project,
    each script that compiled uses its new source). Closing a SourceWindow
    drops edits not compiled; opened again, it shows the source as last
    compiled.
  - The program starts by itself the first time the window is opened, once
    it is in the Viewport and laid out (a MobileLaunchWindow is fitted to
    its phone screen first), as if Go were pressed. Restoring the window
    after minimizing or hiding it does not run it again. Pass
    autoStart: false to the constructor to wait for Go instead.
  - go(), stop() and reset() are done by a ProgramRunner (window.runner),
    shared with the ?app= page.
  - go() stops any previous run, clears the text panel and removes the
    program's widgets, and runs the source
    on the Scheduler shared with the consoles, in the launching console's
    language (ConsoleWindow.spawn). Output, and load and runtime errors,
    appear in the text panel; the StatusBar reports when it starts and ends.
  - reset() stops the program, clears the text panel and removes the
    program's widgets.
  - Closing a launch window stops its program.

DesktopLaunchWindow
  - An ordinary window, 640 x 440 to start, that can be moved, resized,
    minimized and maximized.

MobileLaunchWindow
  - Preset to the size of a phone: the content area is exactly
    MobileLaunchWindow.screenSize, 360 x 640 CSS pixels, whatever the
    theme's title bar and borders (it is re-fitted when the theme changes).
  - It cannot be resized or maximized (resizable is false), but can be
    moved and minimized.
  - When opened it moves up, if need be, so it does not reach below the
    StatusBar.
  - Its text output is 2px larger than the theme's font size, and its
    colour is the theme's text colour mixed 25% towards black.
  - Its content is a Stack (window.stack) holding the app's screen and, once
    Show source is first pressed, the editable source (window.sourceEditor,
    a SourceEditor, whose view is window.sourcePanel:
    a code editor, or for a project one tab per script). The Show source
    button switches between them (toggleSource()) and reads Show output
    while the source is showing; showSource() and showOutput() pick one,
    and window.showingSource says which is showing. Go shows the output
    before it runs the program. No SourceWindow is opened. The Compile
    button (window.compileButton) is shown only while the source is, and
    enabled only when it has been edited since it was last compiled.


TranscriptWindow (singleton)
----------------------------
A Window showing the transcript: a log shared by every console.

  - There is only one; TranscriptWindow.instance creates it on first use,
    and constructing a second one throws.
  - Its content is a TextPanel (transcriptWindow.textPanel). Each call to
    the Transcript built-in from a BasicConsoleWindow appends one line to it and
    scrolls it into view.
  - Its ButtonBar has a Clear button, which empties the transcript
    (transcriptWindow.clear()).
  - Open at startup and always listed in the Windows menu (see Startup).
  - Closing it only hides it: the instance and its text are kept, and the
    Windows menu reopens it. dispose() discards the instance, and the next
    use creates a new one.


SignInWindow (singleton)
------------------------
A Window for choosing the user this browser works as (File > Sign In).

  - There is only one; SignInWindow.instance creates it on first use. It
    has a fixed size.
  - Its content has a User name field, a line saying who is signed in now
    and a line for errors.
  - Its ButtonBar has Sign In, Sign Out and Cancel. Sign In (or Enter in
    the field) sets the user (setUser in db-client.js) and closes the
    window; a name that is not 2 to 30 letters, digits, - or _ is reported
    and the window stays open. Sign Out goes back to the shared space.
    Cancel (or Escape) closes the window.
  - The server has no credentials yet, so signing in is only giving a name:
    it is the same setting as Settings > User.


RegisterWindow (singleton)
--------------------------
A Window for registering a new user on the database server
(File > Register...).

  - There is only one; RegisterWindow.instance creates it on first use. It
    has a fixed size, and opens with empty fields.
  - Its content has User name and E-mail fields (the e-mail is optional) and
    a note naming the server in use.
  - Its ButtonBar has Register and Cancel. Register (or Enter in a field)
    checks the fields, then creates the user (registerUser in db-client.js,
    POST /users) and signs in as them (setUser). Cancel (or Escape) closes
    the window.
  - On success the RegisterWindow closes and a Toast says who was
    registered. A bad field or an error from the server, such as a name
    already taken, is shown in a NotificationWindow over the window, which
    stays until it is dismissed; the RegisterWindow stays open and the User
    name field gets the focus back.
  - Closing or reopening the window closes its notification.
  - The server has no credentials yet, so registering only reserves the
    name.


NotificationWindow
------------------
A small fixed-size Window that says how something went.

  - NotificationWindow.show(viewport, options, owner) makes one and opens
    it centred over owner (a Window), or in the middle of the Viewport if
    there is none.
  - Options: message; kind, which is 'success', 'error' or 'info' and sets
    the icon, the colour and the default title; title; duration, in
    milliseconds, after which it closes by itself (0, the default, is
    never); and onClose, called once however it closes.
  - Its ButtonBar has OK, which has the focus when it opens. OK, Enter or
    Escape closes it. It has no minimize button.


Toast (src/ui/toast.js)
-----------------------
A short message that pops out from one side of the Viewport, stays a few
seconds and goes away by itself. It is not a Window: it takes no focus, has
no buttons and never covers the menus. Clicking it dismisses it.

  - Toast.show(viewport, options) makes one and opens it.
  - Options: message; kind, 'success', 'error' or 'info' (the icon and
    colour); side, 'top', 'bottom', 'left' or 'right'; duration, in
    milliseconds. Side and duration default to the Settings below.
  - Several toasts on one side stack, newest nearest the edge. Top toasts
    sit under the Navbar and bottom ones above the StatusBar.
  - Settings > Toast Side and Settings > Toast Time choose the default side
    (top) and duration (3 seconds; 1, 2, 3, 5 or 10). Choosing one shows a
    sample toast. The choice is remembered for the next visit
    (toastSide()/setToastSide(), toastDuration()/setToastDuration()).
  - SignInWindow, SignOutWindow and RegisterWindow show a success toast when
    they finish.


CommunityProjectsWindow
-----------------------
A Window listing the projects other users have shared (not the signed-in user's own), so they can be launched or copied, never modified.

  - Its title is "Shared Projects", matching the Navbar button that opens it.
    When other Shared Projects windows are already open, the caption is
    numbered with the lowest free number: "Shared Projects 2", "... 3", and so on.
  - Like a console window, it is not unique: each press of the Shared Projects
    button opens a new one (new CommunityProjectsWindow()). A closed window stops
    listening for user and database server changes.
  - It is an HSplitWindow: a vertical divider splits it, with the project grid on
    the left and a TabPanel for the selected project on the right (the tabs are
    empty while no row is selected):
      Details  the name, owner, number of scripts, update time and description
               (a read-only TextPanel).
      Scripts  the project's scripts in order (a ListPanel, 'name  Language',
               and '· owner' for another user's script); the first is selected.
      Source   the source of the script selected in Scripts (a read-only
               TextPanel), as the project last saved it.
  - The left side is a GridPanel with one row per project another user has shared
    (the Shared box of the project in My Projects), whoever owns it, and the
    columns Name, Owner, Scripts and Updated. Owner is the user whose space the
    project is in, or "(shared)"; Scripts is how many scripts it has; Updated is
    the record's last update (a time for today, else a date). Click a column
    header to sort by it, and again to reverse. Drag the right edge of a header
    to resize a column.
  - Its Launch menu is the same as a console's: Desktop, Mobile, a
    separator and Web. Desktop (also double-click or Enter on a row) and
    Mobile run the selected project, as it was last saved, in a new
    DesktopLaunchWindow or MobileLaunchWindow; Web opens it as a full page
    in a new browser tab. The items are greyed out until a row is
    selected.
  - Copy (greyed out until a row is selected) stores a copy of the selected
    project in My Projects. It opens a CopyProjectWindow, where the name can
    be edited first (a name that is already one of the user's projects is
    refused). The copy is the user's own, unshared, with its own copies of the
    scripts (a script whose name the user already has gets ' 2', ' 3'...), so
    it does not change if the author edits theirs. It needs a signed-in user.
  - The list is read from the database each time the window is opened, by
    Refresh, and when the database server or the user changes. A failed
    read, or no shared projects, shows a note in place of the rows.


FileCopyWindow (singleton)
-------------------------
A Window, opened by File > File Copy, that copies files between two places in
the manner of Norton Commander. The copy engine and the volumes are in
src/ui/file-volumes.js, which needs no DOM.

  - Its title is "File Copy". There is only one; FileCopyWindow.instance creates
    it on first use, and constructing a second one throws.
  - File > File Copy is shown only while the user "admin" is signed in
    (isAdmin() of db-client.js: signIn() succeeded as admin, ADMIN_USER, and
    admin is the current user); otherwise it is hidden, and the window closes
    if the user changes. It
    has no sign-in of its own: the remote server is reached with the token
    from File > Sign In, and the local server, a development server on this
    computer, trusts requests from this computer without one.
  - Two panes side by side. The pulldown of each offers, in this order:
    Local database: <user>'s scripts, Local database: <user>'s projects,
    Remote database: <user>'s scripts and Remote database: <user>'s projects
    (databaseVolumes() of file-volumes.js). The left pane starts on the local
    scripts, the right on the remote ones. Scripts are listed as name.py; a
    scripts pane has no folders and keeps only .py text files. A projects pane
    (ProjectsVolume) lists the user's projects, as My Projects does, each a
    folder holding its scripts as name.py; F7 there makes a new, empty,
    unshared project and F8 on a project deletes it with its scripts (after
    asking). A project copied to the other server's projects pane is made
    there with its scripts. There are no folders on this computer, Browser
    files, or shared scripts or projects here.
  - The active pane is the source; the other is the target. Keys: Tab, arrows,
    Home/End, PgUp/PgDn, Enter (open a folder; .. or Backspace goes up),
    Insert or Space (mark), + - * (mark all, none, invert), F5 copy, F6 move,
    F7 new folder, F8 or Delete delete, F9 refresh, Escape (stops a job). The
    buttons along the bottom do the same. Without marks a command works on the
    file under the cursor.
  - Folders are copied with all they hold. A file that exists in the target
    (names compare ignoring case) is replaced only when asked: Overwrite, Skip,
    Overwrite All, Skip All or Cancel. A mistake with one file is reported and
    the rest go on. A move deletes each source once it is copied.
  - Questions and the folder name are asked on a line above the status line,
    not in a dialog; the status line says what was done.


CopyProjectWindow

Widget (abstract)
-----------------
The abstract base class of every UI element. Widget is never instantiated
directly; only its concrete subclasses are.

  - Owns a DOM element and knows its parent widget (null for the Viewport).
  - Has a position and size, set by its parent during layout.
  - Can be shown or hidden; a hidden widget takes no space.
  - Provides layout() to size and position itself, and dispose() to remove
    itself and release any event listeners.
  - id is a name to find the widget by ('' by default; not the element's
    DOM id). childWidgets lists the widgets directly inside it (a Panel's
    children; a Window adds its ButtonBar), and descendants() walks all of
    them, depth first.
  - findById(id) returns the first widget inside this one with that id, or
    null. findByClass(cls) returns every widget inside it of a class: a
    constructor (subclasses match too), or a program class name such as
    'Button' (matched against programClass, which program widgets carry;
    class names cannot be matched by constructor name because the bundle
    is minified).


Viewport (singleton)
--------------------
The outermost container. It fills the whole browser window and is the root
of the widget tree.

  - Exactly one instance exists; obtain it with Viewport.instance. Calling
    the constructor a second time is an error.
  - Holds an optional Navbar docked at the top, an optional StatusBar docked
    at the bottom, and one content widget that fills the space between.
  - Hosts Windows, which float above the content area. The Viewport keeps
    their stacking order and brings a window to the front when it is
    clicked.
  - content is the widget filling the space between the Navbar and the
    StatusBar (or null); Windows float above it. Any widget with a height
    can be docked as the StatusBar (the ?app= page docks a ButtonBar).
  - Listens for browser resize events and lays out the whole tree again.
  - windows returns the open Windows, back to front.
  - visibleWindows and minimizedWindows return the Windows that are
    showing, and those that are minimized.
  - arrangeWindows() cascades the showing Windows diagonally from the top
    left, each sized to 35% of the Viewport's width and height and offset
    30px from the one behind it, front-most last and on top; minimizeAll(),
    restoreAll() (un-minimize and un-maximize) and closeAll() act on every
    Window. The playground's Windows menu offers all four above its list
    of windows.


Panel (abstract)
----------------
A widget that contains other widgets. Panel is never instantiated directly;
subclasses decide how the children are arranged.

  - add(child), remove(child), and a read-only children list.
  - Adding a child sets the child's parent; a widget can belong to only one
    panel at a time.
  - Subclasses implement layout() to place their children, then ask each
    child to lay itself out.
  - Optional padding around the children and spacing between them.
  - Every widget has a box, from the outside in: a margin (clear space
    inside the area its parent gives it), a border (borderWidth pixels, in
    borderColor, or the widget's colour when none is set) and padding
    (between the border and the contents). All are whole pixels, 0 or more,
    and can differ by side: setMargin(n) sets all four sides, and
    setMarginSides(top, right, bottom, left) sets each (likewise padding and
    border width). getMargin() and the like read the top side. A saved design
    holds one number when the sides are alike, else [top, right, bottom, left].
    A row or column counts a child's margin in the space it asks for, and
    keeps its own children inside its border and padding. A Panel's
    children are placed by box, inside its border; padding is drawn by
    Labels and Buttons and used by rows and columns (other classes ignore it).
    A Window has no box.


HPanel and VPanel
-----------------
(src/ui/widgets/hpanel.js, vpanel.js)
Panels that arrange their children in a single row or column.

  - HPanel places children left to right; VPanel places them top to bottom.
  - Each child has either a fixed size or a flex weight along the main axis.
    Fixed-size children are placed first, and the remaining space is shared
    among flex children in proportion to their weights.
  - On the cross axis, children stretch to fill the panel by default.
  - Nesting HPanels and VPanels builds grid-like layouts.


Composite, Stack and the layouts
--------------------------------
(src/ui/widgets/composite.js, stack.js; src/ui/layouts/)
Modelled on qooxdoo's containers (qx.ui.container.Composite and Stack) and
layout managers (qx.ui.layout). Not to be confused with a saved composite
(a widget kept by name in the database): the class Composite is a container.

Composite is a Panel whose children are placed by a layout manager.
  - composite.layoutManager is the layout: set it from a name ('hbox') or a
    Layout; layoutName reads the name. The default is 'basic'. Changing the
    layout places the children again and drops the old layout's settings.
  - A layout works out a box for each visible child and calls
    child.setBounds(...). The box includes the child's margin. Positions are
    inside the Composite's border and padding, so padding is the space
    between the Composite's edge and the layout's area.
  - A child's size comes from, in order: the size the program fixed
    (setWidth / setHeight), what the layout says (flex, a stretch, a cell),
    and the size the child asks for (preferredWidth / preferredHeight).

Stack is a Panel that shows one child at a time, each filling the area. The
first child added is showing. select(i), selectNext() and selectPrevious()
(wrapping round) change it and fire select with the index. The Stack sets its
children's visibility (a TabPanel without the tabs); a saved Stack records
which page shows, and its pages are not saved as hidden. Its layout is
'grow'.

The layouts (LAYOUTS in src/ui/layouts/index.js), after qooxdoo's:

  basic   Children sit where their box says (left, top, width, height), or
          fill the area after fill(). The default.
  canvas  Like basic, but a child can instead be placed by its distance from
          the edges and its size: left, top, right, bottom, width, height,
          each a number of pixels or a percentage ('50%'). Two of the three
          on an axis fix both position and size.
  grow    Every child fills the area. (What a Stack uses.)
  hbox    A row. Each child is as wide as, in order: its fixed width; a
  vbox    share of the space left over, by its flex; the width it asks for.
          Across the row it fills the height unless it has an alignment
          (alignY), when it takes the height it asks for and sits at the top,
          middle or bottom. A VBox is the same down a column (alignX across).
          Options: spacing; alignX (hbox) / alignY (vbox): where the group
          sits when there is space left and no child has flex; reversed.
  dock    Children attach to the edges in the order they were added: a north
          or south child takes the full width left and the height it asks
          for, a west or east child the full height left and its width;
          what remains goes to the center children (the default edge).
          Options: spacingX, spacingY.
  flow    Children side by side, wrapping onto a new line when the next one
          would not fit. Options: spacingX, spacingY, alignX (where each
          line sits), reversed. A child's alignY sits it in its line.
  grid    Rows and columns. A child names its cell (row, column) and how
          many rows and columns it covers (rowSpan, columnSpan). Each track
          is as big as its biggest child unless it has a size; it may have a
          flex, a min and a max. Spare space (or a shortfall) is shared
          among the tracks with flex, within their min and max. A child that
          spans tracks widens the last one it covers that has no size. A
          child fills its cell unless it has an alignment. Options:
          spacingX, spacingY, and per column / row: flex, size, min, max.

Left out: qooxdoo's Atom layout (an icon and a label), as the toolkit has no
icons.

A child's own settings in its parent's layout are child.layoutProps:
{ edge, row, column, rowSpan, columnSpan, alignX, alignY, canvas }, where
alignX is left, center or right, alignY is top, middle or bottom, edge is
north, south, west, east or center, and canvas is six lengths (left, top,
right, bottom, width, height; '' for not set). A layout ignores the ones it
has no use for. cleanChildProps() checks them.

A Composite is saved as { class: 'Composite', layout, layoutOptions,
children }: layout is left out when it is 'basic', and layoutOptions holds
only the settings that differ from the layout's defaults (a grid's as
columns / rows: { index: { flex, size, min, max } }). A child's settings are
saved as layoutProps. A saved Stack has selected (the page showing, left out
when 0) and children.


GroupBox, CheckGroupBox and RadioGroupBox
------------------------------------------
(src/ui/widgets/group-box.js)
Modelled on qooxdoo's qx.ui.groupbox. A GroupBox is a Composite in a frame,
under a title; a CheckGroupBox has a check box in the title and a
RadioGroupBox a radio button. A program can make the last two (a plain
GroupBox is the toolkit's base class of both).

  - The children are placed by a layout manager like a Composite's, inside the
    frame and below the title. The default layout is vbox, not basic.
    A layout takes the room the title and frame need from the container's
    frameInsets ([top, right, bottom, left]; inner() in layouts/layout.js
    subtracts it with the padding): the title row is LEGEND_HEIGHT (24) high,
    and the frame is FRAME_WIDTH (1) wide with FRAME_PADDING (6) inside it.
    The box's own padding comes on top of that.
  - text is the title. checked is the state of the check box or radio button.
    A CheckGroupBox starts checked, a RadioGroupBox not. A plain GroupBox has
    no state: reading checked gives false, and setting it is an error.
  - While the box is not checked its content is disabled: the children are
    dimmed (class cr-groupbox-off) and made inert (element.inert), so they take
    neither clicks nor the keyboard. Children added later are inert too; a child
    taken out is usable again. contentEnabled says which.
  - A change of state fires a change event with detail { checked }, whether the
    user or the program made it.
  - Checking a RadioGroupBox unchecks the others in its group, and they fire
    their change events first. The group is the RadioGroupBoxes in the same
    container; with group set to a name it is every RadioGroupBox with that name
    in the same tree of widgets, wherever they are. Unnamed boxes and named boxes
    are never in a group together. Nothing is checked at first, and a program
    can uncheck the one that is (unlike an HTML radio button, which cannot be
    cleared by the user). Checking two before they are in the same tree leaves
    both checked, so check the one to start with after adding them.
  - For a program: CheckGroupBox(text) and RadioGroupBox(text), with the
    container and layout methods of a Composite, setText / getText,
    setChecked / isChecked, onChange (called with the box and whether it is
    checked now) and, for a RadioGroupBox, setGroup / getGroup. They are saved
    with text, checked (when not the class's default), group and layout (when not
    vbox), and the designer offers them like a Composite.


HSplitPanel and VSplitPanel
---------------------------
(src/ui/widgets/hsplit-panel.js, vsplit-panel.js)
Panels with exactly two children separated by a divider the user can drag.
Both share an abstract SplitPanel base.

  - HSplitPanel places its children side by side with a vertical divider;
    VSplitPanel stacks them with a horizontal divider.
  - The divider position is stored as a fraction (0.0 to 1.0) so the split
    keeps its proportions when the panel is resized.
  - Each side can have a minimum size; the divider cannot be dragged past
    it.
  - Fires a change event when the divider moves, so the position can be
    saved and restored.
  - Double-clicking the divider may reset it to its default position.


Window
------
A top-level panel that floats above the Viewport's content.

  - Has a title bar showing a title and minimize, maximize and close
    buttons, and a content area that holds a single child widget.
  - Moved by dragging the title bar; it is kept within the Viewport so the
    title bar can always be reached.
  - Resized by dragging its edges or corners, down to a minimum size.
  - close() removes the window from the Viewport. A close event is fired
    first, and a handler may cancel it (for example, to confirm unsaved
    changes).
  - Clicking anywhere in a window brings it to the front; isFront tells
    whether it is the front-most window.
  - The front-most window that is showing is the active window: it has
    the stronger title bar and shadow, and the others are drawn inactive.
    isActive tells whether a window is the active one.
  - minimize() hides the window; open() restores it. In the playground each
    minimized window gets a button on the StatusBar, and the Windows menu
    restores it too. minimized tells whether it is minimized.
  - maximize() makes the window fill the Viewport between the Navbar and
    the StatusBar, and keeps it fitted when the browser is resized; restore()
    puts it back where it was. toggleMaximize() switches between the two, and
    double-clicking the title bar calls it. A maximized window cannot be
    moved or resized; maximized tells whether it is maximized.
  - Minimizing, restoring, maximizing and un-maximizing fire a windowstate
    event that bubbles up to the Viewport.
  - Has a ButtonBar (window.buttonBar) along its bottom edge, 30px high,
    below the content area. Subclasses add their buttons to it.
  - The resizable option (true by default) can be set to false for a window
    of fixed size: it has no resize edges and no maximize button, and
    cannot be maximized (double-clicking the title bar does nothing).
    arrangeWindows() moves such a window without resizing it.


TextPanel
---------
A Panel that contains a single text area filling its entire area.

  - The text area is created by the panel and always sized to match it; no
    other children can be added.
  - Exposes the text through a text property (get and set), and fires a
    change event when the user edits it.
  - Can be made read-only, e.g. for program output.
  - focus() moves the keyboard focus into the text.
  - Ctrl+Enter (Cmd+Enter on a Mac) fires a submit event.


MonacoPanel
-----------
A TextPanel whose text is edited in a Monaco editor (the editor behind VS
Code), highlighted for a Monaco language id: new MonacoPanel({ text,
language }), e.g. language 'vb' for VB.NET.

  - Monaco is loaded from cdn.jsdelivr.net the first time a MonacoPanel is
    created, and shared by every later one. Until it arrives the panel works
    as a plain TextPanel; the text typed meanwhile carries over into the
    editor. If it cannot be loaded (e.g. offline), the panel stays a plain
    TextPanel.
  - The text and readOnly properties, focus(), append() and the change and
    submit events work the same with or without the editor.
  - ready is a promise that resolves once the editor is up (to the editor,
    or null if Monaco could not be loaded).


GridPanel
---------
A Panel that is filled by a single table: a header row of column names and
one row per record. Like ListPanel, it tracks the selected row by value and
fires a select event; the keyboard moves the selection.

  - new GridPanel({columns: [{label, width?}], rows, emptyText}).
  - Rows are {value, cells, sort?} objects: cells are the text shown, and
    sort (optional) is what the column is sorted by instead of the text.
    emphasis: true shows a row in bold (a topic with unread posts); title
    is a tooltip for the row.
    rows (get and set) keeps the selected row through a refresh.
  - Clicking a column header sorts by that column; clicking it again
    reverses the order. The header stays in view as the rows scroll.
  - Dragging the right edge of a header resizes that column (at least 40px).
    The first drag fixes every column at its current width; any space left
    over stays empty at the right, and if the columns are wider than the
    panel it scrolls sideways. columnWidths gets the widths in pixels and
    setColumnWidth(index, width) sets one.
  - No other children can be added.


ListPanel
---------
A Panel that is filled by a single List element.

  - The List is created by the panel and always sized to match it; no other
    children can be added.
  - Items are added, removed or replaced through the panel, and the List
    scrolls when they do not fit.
  - Tracks the selected item and fires a select event when the user picks
    one (by click or keyboard).
  - Items are {label, value} objects: items (get and set), addItem(item),
    removeItem(index) and replaceItem(index, item). The selection follows
    the item's value, so replacing all the items keeps the same row
    selected. selectedIndex, selectedItem and select(index) give access to
    it; Up, Down, Home and End move it.
  - An optional emptyText is shown when there are no items.
  - An item may also have header: true (a heading between groups of rows,
    never selected and skipped by the keys), icon (a symbol before the
    label), detail (a short text at the right, such as a count), badge:
    true (shows the detail as a highlighted pill) and title (a tooltip).


TabPanel
--------
A Panel showing one of several pages at a time, chosen by a row of tab
labels.

  - new TabPanel({ tabPosition }): the labels run along the 'top' (the
    default) or the 'bottom' edge, in a 24px strip; the page showing fills
    the rest.
  - addTab(label, widget) adds a page and returns the widget. Pages are
    added only this way; add() is an error. The first page added is
    selected.
  - Clicking a label shows its page and hides the others. select(index or
    label) does the same from code, and fires a select event with detail
    {index, label, widget}.
  - labels, selectedIndex, selectedLabel and selectedWidget describe the
    tabs and the page showing. remove(widget) removes a page and its tab.


OutputPanel
-----------
The output side of a ConsoleWindow: a TabPanel with its labels along the
bottom and four pages.

  - Text: a TextPanel (outputPanel.textPanel) that programs print to. It is
    selected at first. It is writeable: the user can type in it and edit
    what was printed; programs print at its end.
  - Board: a BoardPanel (outputPanel.boardPanel).
  - Canvas: a CanvasPanel (outputPanel.canvasPanel).
  - Physics: a PhysicsPanel (outputPanel.physicsPanel): the Physics class's
    world of falling, bouncing shapes.
  - selectedTab is the label of the page showing; selectTab(label) shows
    another.
  - clear() empties the pages: the text, the board, the canvas and the
    physics world's shapes. No other children can be added.


PhysicsPanel
------------
The Physics page of an OutputPanel: the Physics class's world, a box of
shapes that fall under gravity, bounce, spin and push each other (circles,
balls, rectangles, ellipses and regular polygons; see "The Physics" in
docs/crumb-v0.1-spec.md).

  - The world has a size of its own in units (400 by 300 until the program's
    setSize), with (0, 0) at the top left and y down, and is scaled to fit the
    panel, keeping its shape, as the Canvas is. panel.world is the
    PhysicsWorld of physics.js, the engine, which needs no DOM; the panel
    draws it.
  - Until a program makes its Physics the page shows a demo ball: click to kick
    it. startProgram() gives a program a new, empty world; reset() (before
    each run) puts the demo back; clear() (Clear Output) removes the shapes.
  - A click fires a physicsclick event with the x and y of the world.
  - The world moves only while the page is showing: it pauses when the page is
    hidden or the panel leaves the document, and goes on when it is shown. A
    shape that stays still for half a second falls asleep, and when every
    shape is asleep nothing is animated (no frames) until something changes.
  - Composite shapes are bodies of several parts (physics.js: Body, Part). The
    panel draws world.bodies part by part, at each part's world pose, so a
    group looks like its shapes together; labels come from world.parts.
    Animations (moveTo, rotateTo, scaleTo, oscillate) run inside the engine's
    step, so the panel only has to keep drawing while the world is awake.
  - A PhysicsPanel holds only its canvas.


BoardPanel
----------
The Board page of an OutputPanel: a Panel divided into equally sized
rectangular cells, for board games such as checkers, chess and tic-tac-toe.
new BoardPanel({ rows, columns, checkered, squareCells }); a board is 8 by 8
and checkered unless told otherwise.

  - Rows and columns are numbered from 0: row 0 is the top row and column 0
    the left column. A row or column that is not on the board is a
    RangeError.
  - rows and columns give the size; setSize(rows, columns) changes it (1 to
    100 each) and empties the board.
  - The cells fill the panel, so they are rectangles of the panel's shape.
    Set squareCells to keep them square; the board is then centred.
  - checkered colours the cells alternately light and dark, the top-left
    cell light. A board that is not checkered (tic-tac-toe) is all light.
    The colours come from the theme (board-light, board-dark, board-line,
    board-text, board-selected).
  - Each cell holds a short text - a piece, such as "X" or a chess glyph -
    centred in it and sized to the cell: setText(row, column, text) and
    getText(row, column). "" is an empty cell.
  - A cell can have colours of its own, e.g. to show the legal moves:
    setBackground(row, column, color) and setColor(row, column, color) for
    its text, with getBackground and getColor. "" restores the board's.
  - select(row, column) frames one cell as selected and clearSelection()
    none; selected is { row, column } or null. Both fire a select event
    (detail { row, column }, or null).
  - Clicking a cell fires a cellclick event with detail { row, column,
    text }. A click does not select the cell; the listener decides.
  - clear() empties every cell's text and colours and the selection, and
    keeps the size. No widgets can be added.
  - Programs reach a BoardPanel as their Board (New Board() / Board()); see
    "The Board and the Canvas" under Program widgets.


CanvasPanel
-----------
The Canvas page of an OutputPanel: a Panel that shows a drawing - 2D and
simple 3D graphics, for showing data and for games.
new CanvasPanel({ width, height }).

  - The drawing has a size of its own, in units: 400 by 300 unless told
    otherwise (width, height; setSize(width, height), 1 to 4000 each,
    erases it). (0, 0) is the top left, x goes right and y down. The
    drawing is scaled to fit the panel, keeping its shape and centred, so
    coordinates mean the same at any window size. It is kept at two pixels
    to the unit, so it stays sharp when shown larger.
  - Settings: background (what clear() fills with; white), color (what is
    drawn next; black), lineWidth (1) and fontSize (14), in units. Colours
    are any CSS colour. They are not themed: a drawing looks the same in
    every theme.
  - 2D shapes are painted as they are drawn and stay until clear():
    point(x, y); line(x1, y1, x2, y2); rect and fillRect(x, y, width,
    height); circle and fillCircle(x, y, radius); triangle and fillTriangle
    (three points); polygon and fillPolygon(points), each point [x, y];
    text(x, y, text), with (x, y) its top left.
  - 3D shapes: line3d, triangle3d and fillTriangle3d (points x, y, z),
    box3d and fillBox3d(x, y, z, width, height, depth), centred on (x, y,
    z). x is to the right, y up and z toward the viewer. They are kept in a
    list (at most 20000; clear() empties it) and drawn over the 2D drawing,
    farthest first, each time the drawing is shown. Solid ones are shaded by
    how they face a fixed light. A shape that reaches behind the camera is
    not drawn. This is drawing with the 2D canvas, not WebGL: shapes that
    pass through each other are not cut where they cross.
  - The camera: setCamera(x, y, z) puts it somewhere (it starts at 4, 3, 6);
    lookAt(x, y, z) is the point it looks at (the origin); orbit(angle,
    height, distance) puts it on a circle round that point, angle in
    degrees. Because the shapes are kept, moving the camera and showing
    the drawing again gives the new view without drawing them again.
  - autoUpdate (true at first): each change is shown by itself, at the
    browser's next frame. A game turns it off and calls update() when each
    picture is complete, so a half-drawn picture is never seen.
  - Input: a click fires a canvasclick event with detail { x, y }, in
    units, and gives the canvas the keyboard; a key going down fires
    canvaskey with detail { key }. isKeyDown(key) says whether a key is
    held; mouseX and mouseY are where the mouse last was. Keys are named
    in lower case, without "Arrow": "a", "left", "space", "enter"
    (isKeyDown takes any case).
  - reset() puts everything back as new. No widgets can be added.
  - Programs reach a CanvasPanel as their Canvas (New Canvas() /
    Canvas()); see "The Board and the Canvas" under Program widgets.


Navbar (singleton)
------------------
The navigation strip docked along the top of the Viewport. Navbar is a
subclass of HPanel, so its contents are laid out left to right using the
same fixed-size and flex rules.

  - Exactly one instance exists; obtain it with Navbar.instance. Calling
    the constructor a second time is an error.
  - Added to the Viewport (viewport.navbar = Navbar.instance), which docks
    it at the top of the page.
  - Is 35px high and spans the full width of the Viewport. Windows cannot
    be dragged above it.
  - Its children are a title or logo on the left and the navigation items,
    typically Menus; a flex spacer can push items to the right-hand end.
  - Each item has a label and an action; the active item is highlighted.
  - Items that do not fit may collapse into an overflow menu on narrow
    screens.


StatusBar (singleton)
---------------------
The status strip docked along the bottom of the Viewport. StatusBar is a
subclass of HPanel.

  - Exactly one instance exists; obtain it with StatusBar.instance. Calling
    the constructor a second time is an error.
  - Added to the Viewport (viewport.statusBar = StatusBar.instance), which
    docks it at the bottom of the page.
  - Is 24px high and spans the full width of the Viewport. Windows cannot
    be dragged below it.
  - A message Label on the left (message, or show(text, tone) where tone
    'error' shows it in red) and an info Label on the right (info).
  - setTasks([{label, title, action}]) shows a row of buttons between the
    message and the info; the playground uses it for minimized windows.
  - In the playground the consoles report on the message (running, finished,
    stopped, load errors) and the info shows a live summary of the
    scheduler's processes.


Menu
----
A pulldown menu: a labelled button that opens a list of items when clicked.
Menu is a Widget, not a Panel; its items are not widgets.

  - addItem(label, action, { checked, enabled }) adds an item. Choosing the
    item closes the menu and runs action(). If enabled is given, it is
    called each time the menu opens and the item is greyed out and cannot be
    chosen while it returns false.
  - addSubmenu(label, items) adds an item with an arrow that opens a
    submenu beside it (to the right, or to the left if there is no room)
    when pointed at or clicked. items is a function called each time the
    submenu opens, returning items in the itemsProvider shape. Only one
    submenu is open at a time, and choosing an item in it closes the menu.
  - addSeparator() adds a dividing line; an itemsProvider can return
    {separator: true} for the same.
  - If checked is given, it is a function called each time the menu opens;
    a check mark is shown next to the item while it returns true.
  - Only one menu is open at a time. Clicking outside the menu or pressing
    Escape closes it.
  - The list is drawn above all Windows, and kept inside the browser window:
    it opens below the menu's button, or above it when there is no room
    below (as for a menu in a Window's ButtonBar).
  - In a ButtonBar a Menu is drawn like the Buttons beside it, with a small
    down arrow after its label.
  - Setting itemsProvider to a function makes the menu dynamic: the function
    is called each time the menu opens and returns the items to show, in the
    same {label, action, checked, enabled} shape. "(none)" is shown for an
    empty list.


Startup
-------
Crumb.ui.start() picks the UI for the device (isMobileDevice() in
src/ui/device.js): on a phone it calls startMobile(), otherwise
startDesktop(). A ?ui=mobile or ?ui=desktop page parameter overrides the
detection. A phone is a browser that reports itself as mobile, a mobile
user agent, or a touch screen whose short side is under 600px; tablets get
the full UI.

The mobile UI (src/ui/mobile/app.js) is, for now, a single landing page
with the name, a short description, a link to the full version
(?ui=desktop) and the build time. It uses plain DOM and the theme
variables, not the desktop widgets.

When the full UI starts, the Navbar is docked at the top of the Viewport
with, from left to right, a File menu, a Database menu, Basic, Python,
Process and Designer buttons, a Settings menu, and a Windows menu, which is always the
last menu. At the right end is the time the page was built, e.g.
"Built 2026-09-23 13:47:05 UTC". The
StatusBar is docked at the bottom, and the TranscriptWindow is open.

  - The Help menu, after the My Projects and Shared Projects buttons, has Widget
    Documentation, which opens the WidgetHelpWindow.
  - The File menu starts with Sign In, which opens the SignInWindow, and
    Register..., which opens the RegisterWindow, then a separator. It then has New Basic and New Python; then Open..., Save and
    Save As...; then Delete, with a separator between the groups.
    - New Basic and New Python open an empty console in that language.
    - Open... asks for a source file and opens it in a new console: .bas
      files in a BasicConsoleWindow, .py files in a
      PythonConsoleWindow. The console's title shows the file name.
    - Save writes the front-most console's source back to its file; for a
      console with no file yet it does what Save As... does.
    - Save As... asks where to save the front-most console's source.
    - Save and Save As... are greyed out unless the front-most showing
      window is a console.
    - Delete asks for confirmation, then deletes the front-most console's
      file. The source stays in the console, which no longer has a file.
      It is greyed out unless that file was opened or saved through the
      File System Access API (Chrome, Edge), since other browsers give a
      page no way to delete files.
    - Where the browser has the File System Access API (Chrome, Edge), Save
      writes the file in place. Elsewhere Open uses a file chooser and Save
      downloads the file.
  - The Database menu has Basic and Python items, which open the
    BasicDatabaseWindow and PythonDatabaseWindow (or bring them to the
    front).
  - The Basic button opens a new BasicConsoleWindow.
  - The Python button opens a new PythonConsoleWindow.
  - The Process button opens the SchedulerWindow (or brings it to the
    front).
  - The Designer button opens a new DesignerWindow (the GUI designer).
  - The Settings menu has three items that open submenus, each with a check
    mark on the choice in use. Choosing one takes effect at once and is
    remembered for the next visit.
    - Theme: Classic, Apple or Steampunk.
    - Code Font: JetBrains Mono (the default) or IBM Plex Mono, used for
      source, output and lists, and in the Monaco editor. The font is
      fetched from Google Fonts when first chosen; until it arrives, or if
      the page is offline, the theme's own monospace font is used.
    - Database: Remote (https://api.fastblips.com, the
      default) or Local (http://localhost:3000). Open Database windows
      reload from the new server.
  - The Windows menu lists every open window by title, front-most first,
    with a check mark on the front-most one. Choosing a window shows it (if
    hidden) and brings it to the front.
  - The TranscriptWindow is always listed, so choosing it reopens it after
    it has been closed.
  - The My Projects button, after Windows, opens the ProjectsWindow; the Shared Projects button, after it, opens a new CommunityProjectsWindow
    (or brings it to the front).


Button
------
A clickable, labelled Widget.

  - new Button(label, action); clicking it runs action().
  - label and enabled properties.
  - Used on the Navbar and in ButtonBars.


ButtonBar
---------
A row of Buttons along the bottom of a Window. ButtonBar is a subclass of
HPanel.

  - Is 30px high and spans the full width of the Window.
  - addButton(label, action) creates a Button, adds it and returns it.
  - Buttons are left-aligned, in the order they were added.


HSplitWindow
------------
A Window whose content is an HSplitPanel.

  - left and right properties get or set the two sides of the split.
  - Accepts the usual Window options plus left, right and position (the
    fraction of the width given to the left side).


ConsoleWindow
-------------
An HSplitWindow for editing and running code: the shared base of the
language consoles below. Any number of consoles can be open at once.

  - The left side is an editable TextPanel holding the source; the right
    side is an OutputPanel (console.outputPanel) with Text, Board and
    Canvas tabs. console.output is its Text page, which programs print to.
  - Its ButtonBar has, from the left, Run (runs the source), Clear Output
    (empties every page of the OutputPanel) and Clear Input (empties the
    source) buttons. Ctrl+Enter in the source also runs it.
  - After Clear Input comes a Priority menu (console.priorityMenu) with items 1 to 5; the
    chosen one is checked and kept in console.priority (default 3). The
    console's programs run at that priority on the Scheduler (1 highest,
    5 lowest), and choosing one also changes the priority of the program
    running now (setPriority(level)).
  - console.compiled is compiled code that came with the source (a
    record's compiled_code, when opened from a DatabaseWindow). Run and
    Launch use it instead of compiling for as long as the source still
    matches it; see "Compiled code" below.
  - After Priority comes a Launch menu (console.launchMenu), placed like
    the other buttons, with Desktop, Mobile, a separator and Web. They call
    launch('desktop'), launch('mobile') and launch('web'). The first two
    open a new DesktopLaunchWindow or MobileLaunchWindow with a copy of the
    console's source. Web opens the app saved in the database under the
    console's script name as a full page (the ?app= page) in a
    new browser tab; it runs the saved version, not edits made in the
    console, and needs a script that came from the database (console.
    recordName and recordOwner, set when a record is opened in a console):
    otherwise the StatusBar says so. addLaunchItems(menu, launch) in
    launch-window.js builds these items, and launchWeb(name, owner) opens
    the page.
  - A subclass sets its language by overriding the static titlePrefix
    (e.g. 'Basic Console') and defaultText (the starting source), and the
    run() and stop() methods. In ConsoleWindow itself both do nothing.
  - The static spawn(source, { name, output, onExit }) compiles source in
    the console's language and spawns it on the shared Scheduler, printing
    to output (a TextPanel); load errors are written to output instead. It
    returns { process, errorCount } and does not start the scheduler. run()
    and LaunchWindow's Go both use it. In ConsoleWindow it spawns nothing.
  - createInput(text) makes the source pane: a TextPanel unless a subclass
    overrides it (e.g. with a MonacoPanel).
  - Each subclass numbers its own windows: the first is titled with the
    prefix alone, then '<prefix> 2', ... Every new console, of any kind,
    opens slightly below and to the right of the previous one.
  - Closing a console calls stop().


BasicConsoleWindow
------------------
A ConsoleWindow that runs Crumb code, titled Basic Console, Basic Console 2, ...

  - The source pane is a MonacoPanel with VB.NET highlighting.
  - While its program runs, the console's output pane is dimmed a little
    (running is true); it returns to normal when the program ends.
  - Run compiles the source and starts it on the Scheduler shared by all
    consoles (src/ui/runtime.js), so programs run in the background, take
    turns, and a Sleep never freezes the page. Output appears as it is
    printed. Running again, or closing the console, stops its previous
    program.
  - Load and runtime errors are shown in the output, in the section 11
    diagnostic format.
  - Lines written by the Transcript built-in are appended to the
    TranscriptWindow rather than to the console's output.


PythonConsoleWindow
-------------------
A ConsoleWindow for Python code, titled Python Console, Python Console 2, ...

  - Starts with print("Hello, world") as its source.
 

LaunchWindow (abstract)
-----------------------
A Window that runs a console's program as an app. Launch windows are
opened from a console's Launch menu; any number can be open at once.

  - new DesktopLaunchWindow({ source, console }) or
    new MobileLaunchWindow({ source, console }): source is the program and
    console the ConsoleWindow it came from (kept as window.source and
    window.console). The source is a copy taken at launch: editing the
    console afterwards does not change it. The console's class
    (window.language) runs it, so Go still works after the console closes.
  - Titled with the name of the script loaded in the console that launched
    it (console.scriptName): the console's file name, e.g. fizzbuzz.bas;
    for a console opened from a DatabaseWindow, the record's name; otherwise
    the console's title (e.g. Basic Console 2).
  - Each new launch window opens slightly below and to the right of the
    previous one.
  - The content (window.screen) is the app's screen, an AppScreen: a
    TextPanel (window.textPanel) that fills all of it, which the program
    prints to, with the program's widgets (New Button, ...) over it. The
    same in DesktopLaunchWindow and MobileLaunchWindow.
  - Its ButtonBar has Go, Reset and Show source buttons (window.goButton,
    window.resetButton and window.sourceButton), which call go(), reset()
    and showSource(). Show source opens a SourceWindow
    (src/ui/windows/source-window.js) with the source the window runs - the
    copy taken at launch, or for a project one tab per script, in order;
    pressed again it brings that window to the front, and it closes with
    the launch window. In a MobileLaunchWindow the source is instead shown
    on the phone screen, in place of the output (see MobileLaunchWindow).
  - Wherever the source is shown it can be edited (a SourceEditor), and
    there is a Compile button (in the SourceWindow's button bar, or the
    MobileLaunchWindow's while it shows the source). It is enabled only
    while the source differs from the one last compiled (at first, the
    copy taken at launch). compile(editor) compiles the edited source,
    without running it (runner.recompile(texts); for a project only the
    scripts that changed), and every later Go runs that source and its new
    code instead of the compiled code the window was given or this page's
    compile cache; Compile is then disabled until the next edit. Nothing is
    saved to the database or back to the console. A toast says it compiled,
    or how many errors there were and the first; on errors the source and
    code used before are kept and Compile stays enabled (for a project,
    each script that compiled uses its new source). Closing a SourceWindow
    drops edits not compiled; opened again, it shows the source as last
    compiled.
  - The program starts by itself the first time the window is opened, once
    it is in the Viewport and laid out (a MobileLaunchWindow is fitted to
    its phone screen first), as if Go were pressed. Restoring the window
    after minimizing or hiding it does not run it again. Pass
    autoStart: false to the constructor to wait for Go instead.
  - go(), stop() and reset() are done by a ProgramRunner (window.runner),
    shared with the ?app= page.
  - go() stops any previous run, clears the text panel and removes the
    program's widgets, and runs the source
    on the Scheduler shared with the consoles, in the launching console's
    language (ConsoleWindow.spawn). Output, and load and runtime errors,
    appear in the text panel; the StatusBar reports when it starts and ends.
  - reset() stops the program, clears the text panel and removes the
    program's widgets.
  - Closing a launch window stops its program.

DesktopLaunchWindow
  - An ordinary window, 640 x 440 to start, that can be moved, resized,
    minimized and maximized.

MobileLaunchWindow
  - Preset to the size of a phone: the content area is exactly
    MobileLaunchWindow.screenSize, 360 x 640 CSS pixels, whatever the
    theme's title bar and borders (it is re-fitted when the theme changes).
  - It cannot be resized or maximized (resizable is false), but can be
    moved and minimized.
  - When opened it moves up, if need be, so it does not reach below the
    StatusBar.
  - Its text output is 2px larger than the theme's font size, and its
    colour is the theme's text colour mixed 25% towards black.
  - Its content is a Stack (window.stack) holding the app's screen and, once
    Show source is first pressed, the editable source (window.sourceEditor,
    a SourceEditor, whose view is window.sourcePanel:
    a code editor, or for a project one tab per script). The Show source
    button switches between them (toggleSource()) and reads Show output
    while the source is showing; showSource() and showOutput() pick one,
    and window.showingSource says which is showing. Go shows the output
    before it runs the program. No SourceWindow is opened. The Compile
    button (window.compileButton) is shown only while the source is, and
    enabled only when it has been edited since it was last compiled.


TranscriptWindow (singleton)
----------------------------
A Window showing the transcript: a log shared by every console.

  - There is only one; TranscriptWindow.instance creates it on first use,
    and constructing a second one throws.
  - Its content is a TextPanel (transcriptWindow.textPanel). Each call to
    the Transcript built-in from a BasicConsoleWindow appends one line to it and
    scrolls it into view.
  - Its ButtonBar has a Clear button, which empties the transcript
    (transcriptWindow.clear()).
  - Open at startup and always listed in the Windows menu (see Startup).
  - Closing it only hides it: the instance and its text are kept, and the
    Windows menu reopens it. dispose() discards the instance, and the next
    use creates a new one.


SignInWindow (singleton)
------------------------
A Window for choosing the user this browser works as (File > Sign In).

  - There is only one; SignInWindow.instance creates it on first use. It
    has a fixed size.
  - Its content has a User name field, a line saying who is signed in now
    and a line for errors.
  - Its ButtonBar has Sign In, Sign Out and Cancel. Sign In (or Enter in
    the field) sets the user (setUser in db-client.js) and closes the
    window; a name that is not 2 to 30 letters, digits, - or _ is reported
    and the window stays open. Sign Out goes back to the shared space.
    Cancel (or Escape) closes the window.
  - The server has no credentials yet, so signing in is only giving a name:
    it is the same setting as Settings > User.


RegisterWindow (singleton)
--------------------------
A Window for registering a new user on the database server
(File > Register...).

  - There is only one; RegisterWindow.instance creates it on first use. It
    has a fixed size, and opens with empty fields.
  - Its content has User name and E-mail fields (the e-mail is optional) and
    a note naming the server in use.
  - Its ButtonBar has Register and Cancel. Register (or Enter in a field)
    checks the fields, then creates the user (registerUser in db-client.js,
    POST /users) and signs in as them (setUser). Cancel (or Escape) closes
    the window.
  - On success the RegisterWindow closes and a Toast says who was
    registered. A bad field or an error from the server, such as a name
    already taken, is shown in a NotificationWindow over the window, which
    stays until it is dismissed; the RegisterWindow stays open and the User
    name field gets the focus back.
  - Closing or reopening the window closes its notification.
  - The server has no credentials yet, so registering only reserves the
    name.


NotificationWindow
------------------
A small fixed-size Window that says how something went.

  - NotificationWindow.show(viewport, options, owner) makes one and opens
    it centred over owner (a Window), or in the middle of the Viewport if
    there is none.
  - Options: message; kind, which is 'success', 'error' or 'info' and sets
    the icon, the colour and the default title; title; duration, in
    milliseconds, after which it closes by itself (0, the default, is
    never); and onClose, called once however it closes.
  - Its ButtonBar has OK, which has the focus when it opens. OK, Enter or
    Escape closes it. It has no minimize button.


Toast (src/ui/toast.js)
-----------------------
A short message that pops out from one side of the Viewport, stays a few
seconds and goes away by itself. It is not a Window: it takes no focus, has
no buttons and never covers the menus. Clicking it dismisses it.

  - Toast.show(viewport, options) makes one and opens it.
  - Options: message; kind, 'success', 'error' or 'info' (the icon and
    colour); side, 'top', 'bottom', 'left' or 'right'; duration, in
    milliseconds. Side and duration default to the Settings below.
  - Several toasts on one side stack, newest nearest the edge. Top toasts
    sit under the Navbar and bottom ones above the StatusBar.
  - Settings > Toast Side and Settings > Toast Time choose the default side
    (top) and duration (3 seconds; 1, 2, 3, 5 or 10). Choosing one shows a
    sample toast. The choice is remembered for the next visit
    (toastSide()/setToastSide(), toastDuration()/setToastDuration()).
  - SignInWindow, SignOutWindow and RegisterWindow show a success toast when
    they finish.


ApplicationsWindow (singleton)
------------------------------
A Window listing the compiled apps, so they can be launched.

  - Its title is "Applications", matching the Navbar button that opens it.
  - There is only one; ApplicationsWindow.instance creates it on first use,
    and constructing a second one throws.
  - Its content is a GridPanel with one row per compiled app (a program in
    the Basic or Python table saved with its compiled code, from the
    Database window's Compile button) and the columns Name, Owner and
    Updated. Name has "(Python)" after a BlipPy program; Owner is the user
    whose space the app is in, or "(shared)"; Updated is the record's last
    update (a time for today, else a date). Click a column header to sort
    by it, and again to reverse; Updated sorts by time. Drag the right edge
    of a header to resize a column.
  - Its Launch menu is the same as a console's: Desktop, Mobile, a
    separator and Web. Desktop (also double-click or Enter on a row) and
    Mobile run the selected app from its compiled code in a new
    DesktopLaunchWindow or MobileLaunchWindow; Web opens it as a full page
    in a new browser tab. The items are greyed out until a row is
    selected.
  - The list is read from the database each time the window is opened, by
    Refresh, and when the database server or the user changes. A failed
    read, or no compiled apps, shows a note in place of the rows.


WidgetHelpWindow (singleton)
----------------------------
(src/ui/windows/widget-help-window.js, src/ui/widget-docs.js)
A Window, opened by Help > Widget Documentation, that documents every widget a
program can make. It is an HSplitWindow: a ListPanel of entries on the left and
the text of the one chosen in a read-only TextPanel on the right. There is one;
choosing the menu item again brings it to the front.

  - The entries are "All widgets" (an introduction and everything below it, to
    scroll through), "Common methods" (the methods every widget has, in groups),
    then one per class in WIDGET_CLASSES, A to Z. show(label) chooses one.
  - A class's text is its description, its constructor and its methods, in
    BlipPy's spelling with the kind of each argument and result. The
    constructor and methods are made from the class table
    (src/vm/runtime/widgets.js), so they cannot go out of date; the
    description is WIDGET_DOCS in widget-docs.js. Methods every widget has are
    left out of a class and listed once under Common methods
    (WIDGET_CLASSES' common / own fields; the Board, the Canvas and the Physics
    have no common methods, the Viewport only the find methods).
  - test/widget-help.test.js fails when a class has no description, when a
    common method is not described in a group, and when a description names a
    method that does not exist, so a new widget cannot be added undocumented.


SchedulerWindow (singleton)
---------------------------
A Window listing the programs on the UI's shared Scheduler, so they can be
suspended, resumed or killed.

  - Its title is "Process", matching the Navbar button that opens it.
  - There is only one; SchedulerWindow.instance creates it on first use,
    and constructing a second one throws.
  - Its content is a ListPanel with one row per unfinished process: pid,
    name (the title of the console that started it), priority (P1 to P5),
    state (ready,
    running, sleeping, scheduled or suspended) and instructions executed.
    The list is refreshed every 250ms while the window is open, keeping
    the selection.
  - Its ButtonBar has Suspend and Kill buttons, which act on the selected
    process and are disabled when nothing is selected. When the selected
    process is suspended, Suspend reads Resume.
  - Then a Priority menu (items 1 to 5, the selected process's priority
    checked) that changes the selected process's priority.
  - A suspended process gets no turns; a sleeping one keeps the rest of its
    sleep for when it is resumed.


DatabaseWindow
--------------
An HSplitWindow that browses one table of source records on the database
server (rails/server): records are listed on the left ("id  name"), sorted by
name ignoring case, and the selected one is edited in a RecordPanel on the right. Abstract: a subclass
sets the static table ('basic' or 'python', see src/ui/db-client.js),
language (the Monaco language id) and consoleClass. There is one window per
subclass, obtained with BasicDatabaseWindow.instance and
PythonDatabaseWindow.instance; closing it keeps its state.

  - Its ButtonBar has New, Save, Delete, Refresh, Compile and Open in
    Console buttons, a Priority menu (items 1 to 5; the chosen one is
    checked), and a status line at the right end.
  - Priority is the record's priority field (1 to 5, default 3). Choosing
    one marks the record changed; Save stores it.
  - Compile compiles the content in the editor with the consoleClass's
    static compileSource(). On success the chunk is stored as JSON (see
    src/vm/chunk-json.js), with a hash of the source it was compiled from,
    in the record's compiled_code field and the record is saved. On failure nothing is stored or saved; the error count and first
    error show in the status line, with the full text in its tooltip.
  - Selecting a row loads that record. New starts an empty record, which
    Save creates on the server; Save on an existing record updates it.
    Enter in the name, Ctrl+Enter in the content, or Ctrl+S also saves.
  - Delete asks for confirmation, then deletes the record.
  - Selecting another record, starting a new one or closing the window
    with unsaved changes asks before discarding them.
  - Open in Console opens a new console of the table's language holding
    the record's content, with the record's name as its scriptName.
  - The list is reloaded each time the window opens, and by Refresh.
  - The server is the one chosen in Settings > Database: Remote by
    default, or Local when the page is opened with ?db=local.
  - Errors from the server (for example "name can't be blank") or the
    network are shown in red in the status line.

BasicDatabaseWindow edits the Basic programs in the scripts table (VB
highlighting, opens a BasicConsoleWindow); PythonDatabaseWindow edits the
Python ones (Python highlighting, opens a PythonConsoleWindow).


ProjectsWindow (singleton)
--------------------------
An HSplitWindow for the projects on the database server (rails/server),
opened with the My Projects button. A project is a named group of scripts in one
space, with a description. The projects of the page's space (Settings >
User; the shared space with no user) are listed on the left, by name
ignoring case, each with the number of scripts in it; the selected one is
edited in a ProjectPanel on the right.

  - There is only one; ProjectsWindow.instance creates it on first use, and
    closing it keeps its state.
  - Its ButtonBar has two pulldown Menus - Projects (New, Save, Delete,
    Refresh) and Scripts (Edit, Add, Remove, Up, Down) - then a Separator, a
    Launch menu and a status line at the right end. A menu item is greyed
    out when it cannot be used.
  - Launch is the same menu as in a console: Desktop, Mobile, a separator
    and Web. Web opens the project as it was last saved as a full page in
    a new browser tab, at ?project=<owner>/<name> (the page runs every
    script of the project, in order, together on one screen, as Desktop
    does); it is greyed out for a project that is new or has no saved
    scripts.
  - Launch > Desktop or Mobile, as in a console, opens a DesktopLaunchWindow
    or MobileLaunchWindow titled with the project's name that runs all the
    scripts in the list, in order: Go (also automatic when it opens) clears
    the screen once and starts the scripts one after the other on the shared
    scheduler, so they run side by side, printing to the same text panel and
    putting their widgets on the same screen. The list as shown is run,
    saved or not, with the project's copies as they are; a script
    with load errors is reported in the StatusBar and the rest still start.
    The items are greyed out while the project has no scripts.
  - The panel lists the scripts in the project, in order. A project keeps
    its own copy of each script (name, language, source, and priority and
    compiled code if it has them), saved in the project's record.
    Add opens a ScriptPickerWindow with the user's own scripts and the ones
    in the shared space, without any whose name the project already has (names
    are unique in a project, ignoring case); a copy of the one picked goes at
    the end of the list and is selected. Edit opens the project's copy of the
    selected script in a ScriptEditWindow: its Save changes the copy and
    saves the project; the script it was copied from is not changed, and
    changing that script later does not change the copy. Remove takes the
    selected script out of the project, and Up and Down move it one place.
    Add needs a project being edited; the others a selected script, and Up
    and Down room to move.
  - New starts an empty project, which Save creates on the server; Save on
    an existing project updates its name, its description, whether it is
    shared and its scripts in one request, the scripts in their order. Enter in the name, Ctrl+Enter in the description, or
    Ctrl+S also saves. A project needs a name, unique in its space; it may
    have no scripts.
  - The Shared check box beside the name is the project's shared flag (the
    projects table's boolean "shared", false for a new project): checking
    or clearing it is an unsaved change until Save.
  - Renaming a project keeps its scripts. Delete asks for confirmation,
    then deletes the project with its copies of its scripts (the scripts
    they were copied from are kept).
  - Selecting another project, starting a new one or closing the window
    with unsaved changes (including added, removed or moved scripts) asks before discarding them.
  - The lists are reloaded each time the window opens, by Refresh, and when
    the server (Settings > Database) or the user changes.
  - Errors from the server or the network are shown in red in the status
    line.

The stores and the script lists are in src/ui/projects.js, which needs no
DOM.


ProjectPanel
------------
A Panel for editing one project: a Name field, a Shared check box and a
caption along the top, a Description, and a TabPanel filling the rest with three pages: Scripts
(the list of the project's scripts), Strings and Images (empty for now).

  - name, description, shared (true when the Shared box is checked) and
    caption properties; scripts is the list, in
    order ({ id, name, language, owner, shared }) and ids their ids; space
    is the project's space, so that scripts of other users show their owner;
    enabled makes the fields editable or read-only.
  - One script can be selected in the Scripts page, by click or the arrow keys: selectedIndex,
    selectedScript and selectIndex(i). addScript(script), removeSelected()
    and moveSelected(-1 or 1) change the list.
  - Fires change when the user edits a field or the list changes,
    scriptselect when the selection changes, and submit on Enter in the name
    or Ctrl+Enter in the description.


ScriptPickerWindow

A small Window for choosing one script to add to a project. It is given the

  - Its ButtonBar has Add and Cancel. Double-click or Enter on a script also

RecordPanel

A Panel for editing one source record: a Name field and a caption along the

  - name, content and caption properties; enabled makes both fields

  - Fires change when the user edits either field, and submit on Enter in

Label
-----
A Widget showing one line of text (text property). tone = 'error' shows it

Separator
---------
A thin vertical line between the widgets of an HPanel, used to divide the

An empty Widget with a flex weight (1 by default). Placed in an HPanel, it

TextField and PasswordField
---------------------------
(src/ui/widgets/text-field.js)
A single line of text the user can edit, after qooxdoo's qx.ui.form.TextField
and PasswordField. A Widget (not a Panel) on an <input>. Both, and TextArea
(below), are TextInputs: the base that has the text, placeholder, maxLength,
readOnly, enabled, focus() and selectAll().

  - text, placeholder (grey text while it is empty), maxLength (the most the
    user can type; 0 for no limit, and text already there is not cut),
    readOnly, enabled (false greys it out), focus() and selectAll().
  - Events: the browser's own input event on every edit by the user (not when
    the program sets text), and submit, a CustomEvent, when the user presses
    Enter.
  - PasswordField is a TextField that shows dots. It starts empty, and the
    browser is told not to fill in a saved password (autocomplete is
    new-password).
  - A password is never saved. toJson, save and saveComposite leave out a
    PasswordField's text (its placeholder, limit and other settings are kept),
    and building a saved PasswordField ignores any text it holds. The designer
    gives it no Text field and the code generator writes no text for it. The
    program can still read what was typed with getText, so a password typed into
    a program goes to that program: only type one into a program you trust.
  - For a program: TextField(text) and PasswordField(), with setText /
    getText, setPlaceholder / getPlaceholder, setMaxLength / getMaxLength,
    setReadOnly / isReadOnly, setEnabled / isEnabled, focus, selectAll,
    onChange (called with the field and its text) and onSubmit (called with
    the field). The default box is 160 by 28.


TextArea
--------
(src/ui/widgets/text-area.js)
Several lines of text the user can edit, after qooxdoo's qx.ui.form.TextArea.
A TextInput on a <textarea>, so it has everything a TextField has. (A TextPanel
is the older Panel that holds a text area and fills it; a TextArea is a Widget
of its own, with a placeholder, a limit and enabled that a TextPanel lacks.)

  - wrap (true at first): long lines wrap; false lets them run off to the side,
    and the area scrolls. append(text) adds text at the end and scrolls there.
  - Events: input on every edit by the user (not when the program sets the
    text), and submit on Ctrl+Enter or Cmd+Enter. Enter on its own is a new
    line.
  - For a program: TextArea(text), with a TextField's methods, setWrap /
    isWrap and append. The default box is 240 by 120. It is saved with text
    (unlike a PasswordField's), placeholder, maxLength, readOnly, enabled and
    wrap (when not the defaults).


SplitButton
-----------
(src/ui/widgets/split-button.js)
A button with a drop-down arrow beside it, after qooxdoo's
qx.ui.form.SplitButton: clicking the button does its usual thing, and the arrow
opens a menu of related actions ("Save", with "Save As..." under the arrow).

  - A Panel of two parts that it lays out itself (nothing else can be added): a
    Button (the main part, `button`, ending in a straight edge) and a Menu
    (`arrow`, ARROW_WIDTH, 24, wide, labelled with a down arrow). The menu opens
    as any Menu does.
  - label, action and enabled are the Button's (enabled greys out both parts and
    closes the menu); addItem, addSeparator, items, open and close are the
    Menu's. preferredWidth() is the button's plus the arrow.
  - For a program: SplitButton(text), with setText / getText, setEnabled /
    isEnabled, onClick (the button part only: the arrow and the menu are not
    clicks) and the Menu's addItem (the item's handler is called with the button
    and the item's label), addSeparator and clear. setBackground and setColor
    paint both parts. It is saved like a Menu, with its items and handler names,
    and enabled when not true.


SelectBox
---------
(src/ui/widgets/select-box.js)
A drop-down that shows the item chosen from a list, after qooxdoo's
qx.ui.form.SelectBox. A Widget on a <select>, so the list is the browser's own,
and works with the keyboard, a screen reader and a touch screen.

  - Like qooxdoo's, a SelectBox with items always has one chosen: the first item
    added is chosen, and removing the chosen item chooses its neighbour (the next,
    or the last when there is none after). select(-1) chooses none. items,
    count, selectedIndex (-1 for none), selectedText and enabled read the state;
    addItem, removeItem, setItem, getItem, clear and select change it. An index
    out of range is an error.
  - It fires select, a CustomEvent with detail { index, text }, whenever the
    item chosen changes, by the user or the program, including when the first
    item is added. Removing an item before the chosen one changes the index
    without changing the choice, and fires nothing.
  - For a program: SelectBox() with addItem, removeItem, setItem, getItem,
    getCount, clear, select, getSelectedIndex, getSelectedText, setEnabled /
    isEnabled and onSelect (called with the box and the index). The default
    box is 160 by 28. It is saved with items, selected (when not the first, or
    -1 for none) and enabled (when not true).


NavigationBar
-------------
(src/ui/widgets/navigation-bar.js)
The bar along the top of a page of a phone or tablet app: a title in the middle,
a back button on the left and an action button on the right. After qooxdoo
mobile's qx.ui.mobile.navigationbar.NavigationBar. A Widget (not a Panel). The
Navbar is the desktop IDE's own menu strip; this is for programs.

  - title; backText and actionText, the text of the two buttons. A button shows
    only while it has text; both keep their room when hidden, so the title stays
    in the middle. The back button's text follows a chevron.
  - It asks for NAVIGATION_BAR_HEIGHT (44) pixels, a comfortable touch target;
    the default box is 320 by 44.
  - Tapping a button fires back or action, a CustomEvent, on the bar.
  - For a program: NavigationBar(title), with setTitle / getTitle, setBackText /
    getBackText, setActionText / getActionText, onBack and onAction (called with
    the bar). It is saved with title, backText and actionText (when not empty).


Carousel
--------
(src/ui/widgets/carousel.js)
Pages side by side that the user swipes between, with a row of dots saying which
one is showing. After qooxdoo mobile's qx.ui.mobile.container.Carousel. A Panel.

  - Each child is a page and fills the Carousel. The page showing is selected
    (the first one added is); the others wait to its left and right, out of
    sight, and are inert: they take neither clicks nor the keyboard.
  - Dragging sideways with a finger or the mouse (more across than down, past
    DRAG_THRESHOLD, 10 pixels) moves the pages with it. On letting go it goes to
    the next or previous page when the drag covered TURN_FRACTION (0.2) of the
    width, or was a flick faster than FLICK_SPEED (0.5 pixels a millisecond),
    else back. Pointer cancel goes back. At the first and last pages the drag
    resists (a third of the distance). The click that ends a drag is swallowed, so
    it is not a tap on the page under it. The page's own vertical scrolling is
    left alone (touch-action: pan-y).
  - The dots (a row of buttons at the bottom, one a page, the one showing filled)
    can be tapped. dots false hides them; they never show for fewer than two
    pages.
  - select(i), selectNext() and selectPrevious() change the page; the last two do
    nothing at the ends, and select ignores an index that is not a page. Pages do
    not wrap round (a Stack's selectNext does). Each change fires select with
    detail { index, widget }, whoever made it, including when the first page is
    added and when the page showing is removed.
  - For a program: Carousel(), with add, getCount, getChild, clear, select,
    getSelectedIndex, selectNext, selectPrevious, setDots / isDots and onSelect
    (called with the carousel and the index). It is saved with its pages,
    selected (when not 0) and dots (when not true). The default box is 320 by 200.


Drawer
------
(src/ui/widgets/drawer.js)
A panel that slides in over the page from one of its edges, with the page behind
it dimmed: the menu that comes out of the side of a phone app. After qooxdoo
mobile's qx.ui.mobile.container.Drawer. A Composite.

  - A Drawer covers the whole area of the container it is in: a program's Drawer
    starts with fill(), so on the Viewport or in a Composite with a basic, canvas
    or grow layout it fills it. Put it last in its container so it is on top (it
    also has a z-index of 10). In a row or a column it is laid out like any child,
    which is not what it is for. It has no place of its own in the designer.
  - side is one of SIDES (left, right, top, bottom); panelSize is the width of the
    panel (the height, for top and bottom), 260 at first, and never more than the
    area. open slides the panel in and fires change with detail { open }, whoever
    made it; toggle() flips it.
  - Closed, the Drawer takes no clicks (pointer-events: none) and its children are
    inert, so a closed drawer cannot be reached with the keyboard or a screen
    reader. Open, the rest of the area is dimmed.
  - The user closes it in only two ways: a tap on the dimmed area outside the
    panel (unless dismissOnTap is false, when the dimmed area still blocks the
    page behind it), or leaving it unused for the drawer timeout. Escape and
    swipes do not close it. A program can still set open to false.
  - The drawer timeout is Settings > Drawer Time (DRAWER_TIMEOUTS: Never, 3, 5,
    10 or 30 seconds; DEFAULT_DRAWER_TIMEOUT is 5 seconds), remembered in
    localStorage (crumb.drawerTimeout): drawerTimeout() / setDrawerTimeout(ms).
    The wait starts when the drawer opens and starts again on any use of the
    panel (pointerdown, pointermove, keydown, wheel, input, focusin). A drawer's
    own timeout property (ms, 0 for never) overrides the setting; null, the
    default, follows it. A program sets it with setTimeout(seconds) and reads
    the wait in force with getTimeout(), in seconds; it is saved as timeout
    (milliseconds) when set. The designer sets 0 while designing, so a drawer shown
    open there stays open; under Test it follows the setting.
  - The children are in the panel, placed by a layout manager as a Composite's
    are: vbox at first. A layout is given the panel's size, not the area's, so
    that layout() and the panel agree; the Drawer's padding is inside the panel.
  - For a program: Drawer(), with a Composite's methods (add, getCount, getChild,
    clear, setLayout and the layout settings), setSide / getSide, setPanelSize /
    getPanelSize, setOpen / isOpen, toggle, setDismissOnTap / isDismissOnTap and
    onChange (called with the drawer and whether it is open now). It is saved
    with side, panelSize, open and dismissOnTap (when not the defaults), layout
    (when not vbox), fill (true, or false when the program turned it off) and its
    children. In the designer set Open to see it.


Image
-----
(src/ui/widgets/image.js)
A picture from a source address, after qooxdoo's qx.ui.basic.Image. A Widget
(not a Panel) on an <img> element.

  - source: an http: or https: address, or a data:image/ URI; '' shows
    nothing. Anything else (a relative path, file:, javascript:, data: that
    is not an image) is an error, so a shared program can only show pictures
    from the web or ones it carries itself. checkImageSource() checks it.
  - fit: how the picture fills its box: contain (the default: all of it,
    keeping its proportions), cover (fills the box, cropping), fill
    (stretches), none (its own size) or scale-down. These are the CSS
    object-fit values (FITS).
  - alt: text for when the picture cannot be shown.
  - The picture loads in the background. status is 'empty', 'loading',
    'loaded' or 'failed'; naturalWidth and naturalHeight are the picture's
    own size (0 until it has loaded). The widget fires the browser's load
    and error events.
  - Until it has loaded an Image asks for 100 by 100 (the class's default
    box); after, for the picture's own size, and its parent is laid out
    again. A row, column or layout therefore sizes it by the picture
    unless the program fixes a size with setWidth / setHeight.
  - For a program: Image(source) / New Image(source), with setSource /
    getSource, setFit / getFit, setAlt / getAlt, getNaturalWidth,
    getNaturalHeight, isLoaded, onClick, onLoad and onError (the last two
    are called with the image). Register the handlers in the program's
    top-level code, before the picture has loaded. It is saved with source,
    fit and alt (fit and alt only when they are not the defaults).


Ellipse, RoundedRect
--------------------
Filled shapes (src/ui/widgets/shape.js). The fill is the widget's background
(the theme's accent until set) and the outline its colour, drawn borderWidth
pixels wide (2 by default, 0 for none; it is the shape's border, so
borderColor sets its colour apart from the text colour). An Ellipse as wide as it is high is a
circle. A RoundedRect has corners of radius pixels (12 by default; 0 is a
plain rectangle). They have no text, so in a row or column they are as big as
their width and height say (120 by 80 by default). Both take onClick.


Theming
-------
Every colour, font, radius and shadow the widgets use is a CSS custom
property named --cr-*, defined in src/ui/theme.js. Widgets never hard-code
a colour; they write var(--cr-title-bg) and so on.

  - THEMES holds a set of values per theme:
      classic    the default: a Windows 2000-style desktop, with grey 3D
                 bevels, gradient title bars, Tahoma and a blue desktop
      apple      a present-day Mac desktop: a translucent, blurred menu
                 bar, a soft gradient wallpaper, large rounded windows with
                 deep shadows, centred titles, and red, yellow and green
                 circular window buttons on the left whose symbols show
                 on hover
      light      the original flat look
      dark       a dark version of it
      steampunk  dark walnut, mahogany title bars and brass buttons
    Values shared by every theme are defined once, and a theme overrides
    only those it changes. Besides colours there are shape variables:
    window padding, title weight and alignment, raised button and title-bar
    button bevels, the size, shape, colour and order of the title-bar
    buttons (a negative order puts them before the title), rounded and
    blurred menus and bars, the window corner radius (windows have slightly rounded
    corners and soft shadows; a maximized window is square) and how far a
    running console's output fades.
  - Steampunk is a FastBlips theme, defined in
    src/ui/fastblips-themes.js as a small set of tokens (ui: colours, fonts,
    radius, shadow; syntax: editor colours). Choosing one calls applyTheme(),
    which writes the ui tokens on <html> as --fb-* variables, and theme.js
    defines the --cr-* variables in terms of them (fbBridge), so the widgets
    need no change. Each also has its own Monaco theme, built by
    toMonacoTheme() and registered when Monaco loads. Another theme of this
    kind is one more entry in that file's `themes`.
  - Settings > Theme offers Classic, Apple and Steampunk
    (MENU_THEMES). Light and Dark remain available from code. A visitor whose
    saved choice was a theme that has since been removed starts on the default.
  - setTheme(name) switches theme by setting data-cr-theme on <html>, and
    remembers it in localStorage ('crumb.theme'), so the next visit starts
    with it. setTheme('auto') follows the operating system's light or dark
    setting. themeName() is the theme chosen, resolvedTheme() the one in
    effect.
  - A cr-themechange event on document announces each change. The Viewport
    lays everything out again on it (a theme can change fonts, padding and
    borders), and MonacoPanel switches the editor's own theme, since Monaco
    cannot read CSS variables.
  - The code font is separate from the theme (src/ui/fonts.js): it sets
    --cr-font-code, which falls back to the theme's --cr-font-mono, and a
    cr-fontchange event tells Monaco to switch font and re-measure.
  - A new theme is one more entry in THEMES. In the browser the API is
    Crumb.ui.setTheme(...).


ProgramRunner
-------------
Runs one program for the Go and Reset buttons, in LaunchWindows and on the
?app= page (src/ui/program-runner.js). Not a widget.

  - new ProgramRunner({ language, source, screen, name, compiled,
    priority }): language is the
    ConsoleWindow class whose static spawn() compiles the source
    (BasicConsoleWindow or PythonConsoleWindow), screen the AppScreen it
    runs on (it prints to screen.textPanel and puts its widgets on
    screen.host), and name (a string, or a function returning one) the name
    shown in the scheduler and the StatusBar. compiled is compiled code for
    the source (see "Compiled code") and priority the process's priority,
    1 to 5; each may also be a function, read at every Go. Instead of a
    screen, output can give a bare TextPanel; the program then cannot use
    widgets.
  - go() stops any previous run, clears the output and the widgets, and
    starts the source on the shared Scheduler. Output, and load and runtime
    errors, appear in the output; the StatusBar reports when it starts and
    ends.
  - stop() stops the program; reset() stops it and clears the output and
    the widgets.
  - start() starts the source without clearing anything first (go() is
    reset() then start()).
  - ProgramSetRunner({ programs, screen }) runs several programs on one
    screen, for a project's Launch: programs is a list (or a function
    returning one) of { name, language, source, compiled, priority }. go()
    clears the screen once and starts every program in order, so they run
    side by side; stop() and reset() act on all of them; processes lists the
    Processes started and process the last. A LaunchWindow given `programs`
    uses one in place of the ProgramRunner.


The ?app= page
--------------
Opening the page with ?app=<program name> runs that program as a full-page
app instead of the playground (src/ui/run-app.js, startRuntime(name)). It
works on any device, phone included.

  - The browser window (tab) is titled with the program name.
  - The source is read from the database server in use (Settings >
    Database, or ?db=local). ?app=abc is the program abc in the shared
    space; ?app=peter/abc is abc in the user peter's space, and the
    screens it loads by name are peter's too. A Basic program is found
    before a Python one, matching the name exactly, else ignoring case.
    The record's language decides how it runs. The record's compiled_code, if
    it matches the content, is run without compiling, and the program runs
    at the record's priority.
  - The Viewport has no Navbar or windows: its content is an AppScreen that
    fills it (a TextPanel with the program's widgets over it), and a
    ButtonBar with Go, Reset and Show source buttons is docked along its
    bottom.
  - Go and Reset act as in a LaunchWindow (a ProgramRunner does both).
  - A Show source button, after Go and Reset, shows the program's source
    (editable; for a project one tab per script, in order) in place of the
    output, as in a MobileLaunchWindow: the content is a Stack (page.stack)
    holding the AppScreen and the source, the button reads Show output
    while the source is showing, and pressing it switches back. Go shows
    the output before it runs the program. The button is disabled until
    the program has loaded. While the source is showing a Compile button
    (page.compileButton) is shown too; it acts as in a launch window
    (page.compile()): enabled only when the source has been edited since
    it was last compiled, it compiles the edits, later Gos run them, and a
    toast gives the result. Nothing is saved to the database.
  - The program starts by itself as soon as it has loaded from the
    database, as if Go were pressed.
  - While the program loads, the text panel says so and the buttons are
    disabled. If there is no such program, or the server cannot be reached,
    the text panel says so and the buttons stay disabled.
  - ?project=<owner>/<name> (startProjectRuntime(name)) runs a project the
    same way: the page is the same, but it starts every script of that
    user's project, in the project's order, together on the one screen (a
    ProgramSetRunner), each at its own priority and from its own compiled
    code. A name with no owner is looked for in the shared space. A script
    that has been deleted is skipped; if there is no such project, or it
    has no scripts, the text panel says so. The Launch > Web item of the
    Projects window opens it.


Compiled code
-------------
A program runs from compiled code instead of being compiled each time,
wherever it runs in the browser: consoles (Run), launch windows (Go) and
the ?app= page. ConsoleWindow.spawn gets a chunk from loadProgram
(src/vm/program-loader.js), which tries, in order:

  1. The compiled code given with the program (a record's compiled_code,
     made by a DatabaseWindow's Compile button). It is used if it loads
     (right format, made for this instruction set) and records the hash
     of the same source; compiled code left over from before the content
     was edited, or saved without a hash, is ignored and the source
     compiled instead. A record with compiled code and no source runs from
     the compiled code alone.
  2. The page's compile cache: the last 64 programs compiled or loaded,
     by language and source, so running a program again (Run, Go, Reset
     and Go) does not compile it again.
  3. Compiling the source, which adds it to the cache.

Every load builds a fresh chunk (BlipPy's runtime library included), so
two runs never share state. The StatusBar says which was used:
"running (pid 4, compiled code)", "(pid 4, cached)", or just "(pid 4)"
when the source was compiled.


AppScreen
---------
The screen a program runs on, in a LaunchWindow and on the ?app= page
(src/ui/widgets/app-screen.js).

  - A TextPanel (screen.textPanel) fills it: the program's Print output.
  - A BoardPanel (screen.boardPanel), a CanvasPanel (screen.canvasPanel) and
    a PhysicsPanel (screen.physicsPanel) lie over the text, each hidden
    until the program makes its Board, its Canvas or its Physics; it then
    covers the text. The physics world only moves while it is showing.
  - Over it, a transparent layer (screen.widgetLayer, a FreeLayer) holds the
    widgets the program makes. Clicks outside them go through to the text.
    The program's Labels are opaque, so printed text does not show through.
  - screen.host, a ProgramWidgetHost, is what the VM calls to make and
    change the widgets (its `gui` option).
  - clearWidgets() removes them all, and hides the board, the canvas and the
    physics world and puts them back as new (Go and Reset do this).


Program widgets
---------------
Programs build their screens from this toolkit (spec section 10.1). Every
general-purpose class is available, in Crumb as an object made with New and
changed through methods, and in BlipPy the same way with Python spellings:

  Dim label = New Label("Hello")        label = Label("Hello")
  label.setWidth(100)                   label.set_width(100)

  - The classes: Viewport (the screen itself, below), Label, Button, Menu, Spacer, Panel, HPanel, VPanel,
    ButtonBar, HSplitPanel, VSplitPanel, TabPanel, Window, TextPanel,
    MonacoPanel, ListPanel, Ellipse, RoundedRect, Composite, Stack, Image,
    CheckGroupBox, RadioGroupBox, TextField, PasswordField, TextArea,
    SplitButton, SelectBox, NavigationBar, Carousel and Drawer, and the Board
    and the Canvas (below). Left
    out on purpose: the singletons (Navbar, StatusBar, TranscriptWindow,
    SchedulerWindow), the IDE's own windows (consoles, DatabaseWindow,
    LaunchWindows) and panels made for them (RecordPanel, OutputPanel).
  - The Board and the Canvas. New Board() / Board() is the program's
    board, a BoardPanel, and New Canvas() / Canvas() its canvas, a
    CanvasPanel: singletons like the Viewport, but not part of it (they
    have none of the common methods, are not saved by toJson, and the
    designer does not offer them). Where they are depends on where the
    program runs:
      - in a console, the Board and Canvas pages of the console's output;
        a page is shown when the program makes that object. A console has
        no screen, so these are the only classes a program can make there
        (ConsoleOutputHost, src/ui/board-host.js, is the console's host;
        console.outputHost). Each Run starts with the board and the canvas
        as new and the Text page showing; a program that stops with an
        error shows the Text page again, where the error is.
      - on an AppScreen (a launch window, desktop or mobile, the ?app=
        page), the screen's own BoardPanel, CanvasPanel and PhysicsPanel,
        each covering the printed text once the program makes it (the
        canvas over the board). Widgets still float above them.
    New classes go at the end of WIDGET_CLASSES: compiled code names a
    class by its position there.
    The Canvas's methods are the CanvasPanel's: setSize, getWidth,
    getHeight; setBackground, setColor, setLineWidth, setFontSize; clear;
    point, line, rect, fillRect, circle, fillCircle, triangle,
    fillTriangle, text; setCamera, lookAt, orbit, line3d, triangle3d,
    fillTriangle3d, box3d, fillBox3d; setAutoUpdate, isAutoUpdate, update;
    isKeyDown(key), getMouseX, getMouseY; onClick(handler), called with
    the canvas, x and y, and onKey(handler), called with the canvas and
    the key's name. A program in a loop of its own (a game: draw, update,
    Sleep) gets no events until the loop ends, so it asks isKeyDown and
    getMouseX / getMouseY instead. CanvasBinding (src/ui/board-host.js)
    runs these methods for both hosts. examples/canvas-demo.bas and
    canvas-demo.py use it.
    The Board's methods: setSize(rows, columns), getRows, getColumns; setText /
    getText, setBackground / getBackground and setColor / getColor, each
    starting with (row, column); setCheckered / isCheckered and
    setSquareCells / isSquareCells; select(row, column), clearSelection,
    getSelectedRow and getSelectedColumn (-1 for none); clear; and
    onClick(handler). The handler is called with the board, the row and
    the column of the cell clicked - the one event that passes two values
    ('handler:int:int' in the class table). A cell off the board is a
    runtime error. BoardBinding (src/ui/board-host.js) runs these methods
    on a BoardPanel for both hosts. examples/tic-tac-toe.bas and
    tic-tac-toe.py use it.
  - The Viewport. For a program, the topmost GUI object is its Viewport: a
    singleton (New Viewport() / Viewport() always gives the same object)
    that is the FreeLayer of its AppScreen, so a program never reaches the
    IDE's own Viewport. Every widget on the screen is its child, and
    getParent() of such a widget returns it. Its methods: getWidth /
    getHeight (the screen's size), setBackground / setColor, add, getCount,
    getChild, clear, the find methods, toJson, fromJson(text), save(name)
    and load(name).
  - toJson() on any widget gives it and everything in it as JSON text; on
    the Viewport, the whole screen, open and closed Windows included, in
    the format described in docs/viewports-server.md. fromJson replaces the
    screen: the host builds every widget first (so bad JSON leaves the
    screen as it was), then asks the VM to turn each saved handler name
    into a callback (the `resolver` argument of the host interface).
  - Composites: saveComposite(name) on any widget stores that widget and
    everything in it (kind "composite"); vp.loadComposite(name) builds a
    copy on the screen, wires its saved handler names, and returns its
    root. The GUI designer (below) edits them.
  - save(name) and load(name) keep the Viewport in the database's
    viewports table (viewportStore, a SourceStore on /viewports): save
    updates the record with that name or creates one, load fetches it and
    does what fromJson does. Both return promises; the program waits, as
    for Fetch. The server side is in docs/viewports-server.md.
  - Every widget can be given an id (setId) and found from any container
    with findById / findByClass, which use the toolkit's own findById and
    findByClass.
  - A program's Panel is a FreePanel: its children sit where the program
    puts them (the toolkit's Panel is abstract).
  - Composite and Stack (above). A Composite has setLayout(name) and
    getLayout(), where the name (any case) is basic, canvas, dock, flow,
    grid, grow, hbox or vbox, and the layout's settings: setSpacing(n)
    (hbox, vbox: the gap; dock, flow, grid: both spacingX and spacingY),
    setSpacingX / setSpacingY, setContentAlign(x, y) (x for hbox and flow:
    left, center, right; y for vbox: top, middle, bottom; '' for the other
    and for the default), setReversed(b), and for a grid setColumnFlex /
    setRowFlex(index, flex), setColumnWidth / setRowHeight(index, size),
    setColumnMinWidth / setRowMinHeight and setColumnMaxWidth /
    setRowMaxHeight. A setting the layout does not have is a runtime error
    that says what the layout lacks. Every widget has the settings for its
    place in its parent's layout: setEdge(edge) / getEdge, setCell(row,
    column) / getRow / getColumn, setSpan(rows, columns) / getRowSpan /
    getColumnSpan, setAlign(x, y) and setCanvasBounds(left, top, right,
    bottom, width, height). They belong to the widget, so they can be set
    before it is added, and a widget keeps them when it moves. A Stack has
    the container methods, select(i), getSelectedIndex, selectNext,
    selectPrevious and onSelect. A Composite and a Stack are saved, built
    and generated by the designer like the other containers; the designer
    offers the layout's settings and the child's place in the Inspector.
    examples/layouts-tour.py uses each layout.
  - CheckGroupBox and RadioGroupBox (above): a Composite under a title with a
    check box or radio button. Their layout starts as vbox. While unchecked the
    widgets inside cannot be used. A RadioGroupBox unchecks the others in its
    group (the RadioGroupBoxes in its container, or those with the same
    setGroup name) when it is checked.
  - The classes and their methods are one table, WIDGET_CLASSES in
    src/vm/runtime/widgets.js, shared by both languages: each method's
    Crumb name (camelCase), BlipPy name (snake_case), argument kinds and
    result kind. The Crumb compiler checks method names and argument counts
    against it at load time.
  - ProgramWidgetHost (src/ui/program-widgets.js) implements the host
    interface: create(className, args) -> id, has(id), classOf(id) and
    call(id, method, args) -> result. Ids count from 1; each program object
    holds its id. Widgets the host makes itself (a Window's ButtonBar, the
    Buttons made by ButtonBar.addButton) get ids when the program first
    reaches them. A call the program got wrong (an index out of range, a
    Window put inside a panel, a widget put inside itself) throws a
    WidgetError, which the program sees as a runtime error.
  - Layout. A new widget goes on the FreeLayer at its class's default box
    (Label 100 x 24, Button 100 x 32, HPanel 320 x 32, other containers
    320 x 200, ...). On the layer and in a Panel a widget sits at the box
    the program gave it, or fills the area after fill(). In an HPanel,
    VPanel or ButtonBar, setWidth / setHeight set fixedWidth / fixedHeight,
    setFlex sets flex, and otherwise the widget's natural size is used
    (its text's width for Labels, Buttons and Menus; its class's default
    size for the rest). Program Windows float on the layer; they have no
    minimize button, since the screen has no StatusBar to restore them from.
  - Events: onClick, onSelect, onChange, onSubmit, onClose and Menu.addItem
    register handlers. The host calls the VM's callback with the event's
    value (a row or tab index, the new text, the divider position, the
    item's label); the VM queues it and runs the handler, with the widget
    and that value as its arguments, when the program is idle. A program
    with a handler keeps running after its top-level code, waiting for
    events (its process shows as 'waiting' in the Process window), until
    it is stopped. examples/widget-tour.bas and widget-tour.py show most
    of the classes; examples/button-demo.bas is a small one.


GUI designer
------------
DesignerWindow (src/ui/windows/designer-window.js) loads, edits and saves
composite widgets: a widget and everything in it, kept by name in the
database's viewports table (kind "composite"), which a program adds to its
screen with vp.loadComposite(name). Any number can be open; the Navbar's
Designer button opens one.

  - Left: the Outline (the composite as a tree; a tab's label, a split
    panel's side and a window's button bar are shown before the child)
    above the Palette (every widget class but the Viewport). Middle: the
    Preview, the composite built from the real toolkit classes by a
    ProgramWidgetHost of its own, so it looks exactly as it will in a
    program. Right: the Properties of the selected widget.
  - Clicking a widget in the Preview or the Outline selects it; the
    selection is outlined in the Preview, and a widget on a hidden tab has
    its tab shown. In design mode presses never reach the widgets.
  - Where a widget is placed freely (the root, or a child of a Panel) it
    can be dragged in the Preview to move it; a Window root moves by any
    part of it. Every widget is resized by the grip at its corner (in a
    row, column, tab or split that sets its Width / Height, which fix its
    size there; Flex shares out the rest).
  - Drag and drop: a class dragged from the Palette to the Preview or the
    Outline is added where it is dropped. A widget in a row, column, tab
    or split is dragged in the Preview to move it, in its container or
    into another; a marker shows where it would land (a line between
    widgets, a dashed box for inside one). Rows of the Outline are
    dragged the same way: the upper quarter of a row drops before it, the
    lower quarter after it, between them inside it. Nothing can be dropped
    into itself. Escape cancels a drag.
  - Edit: Cut, Copy and Paste (also Ctrl+X, Ctrl+C, Ctrl+V when no text
    field has the focus) work on the selected widget and everything in
    it. The clipboard is shared by every designer. Paste adds a copy inside
    the selection if it can hold one, else after it; ids in the copy that
    the design already uses get a number (save, save2), and a copy in a
    Panel is offset a little.
  - Add (or double-clicking a Palette class) adds a widget of that class
    to the selection when it can hold one - at the end of a list, as a new
    tab, in a split panel's empty side, as a Window's content and then to
    its button bar - or else next to the selection. Delete removes the
    selection (not the root), Up and Down reorder it among its siblings
    (in a split panel, they swap the sides).
  - Properties are grouped: Widget (id and what the class shows: text,
    title, items, tab labels, ...), Place, Box (margin, border width and
    colour, padding: each only on the classes that draw it; written as in CSS,
    one to four numbers: "4" all sides, "2 8" top and bottom then left and
    right, "1 2 3" top, left and right, bottom, "1 2 3 4" top, right, bottom, left), Look (visible,
    colours) and
    Events: the name of the handler for each event the class has - a Sub
    in Crumb, a module-level function in BlipPy - which is looked up in
    the program that loads the composite. Menu items are written one to a
    line as "Label = Handler", with "-" for a separator.
  - The ButtonBar: New (a menu of classes: the new composite's root),
    Open (the saved composites; Refresh list reads them again), Edit
    (Cut, Copy, Paste), the
    composite's name, Save, Add, Delete, Up, Down, Test, which
    switches the Preview between designing and using it, and Code (below).
    The title shows the name and a * while there are unsaved changes;
    New, Open and closing ask before discarding them.
  - Code opens the DesignerCodeWindow
    (src/ui/windows/designer-code-window.js): the Basic or Python program
    that builds the design, which follows the design as it is edited.
    Copy puts it on the clipboard. Save as script keeps it as a script in
    the signed-in user's space. Saving under the name of a script made
    this way again rebuilds only its layout section and leaves the rest
    alone; a script of that name that the designer did not make is never
    overwritten.
  - The program is a header, then a layout section between two
    "DESIGNER LAYOUT" comment lines, then (Crumb) or before (BlipPy, which
    needs a function defined before a call names it) a stub for each
    handler the design names: a Sub or a function with the widget, and
    then the event's value, as parameters. The layout section makes the
    widgets with the same calls a program would write (New Label("x") or
    Label("x"), setId, setBounds where a widget is placed freely,
    setWidth / setHeight / setFlex in a row or column, add, setFirst,
    addTab, setContent, getButtonBar().addButton, ...), then adds the
    root to the Viewport, or opens it if it is a Window. A widget is
    called by its id, or else by its class and a number (label1, button2;
    the root is root, or win). A name that is a reserved word, a built-in
    or already taken gets a number after it. Handler names are exactly
    the design's (a saved composite finds handlers by them) and a widget's
    variable gives way to one: Crumb keeps Subs and variables in one
    namespace. A menu item the design gives no handler gets one made from
    the menu's and the item's words (File, Open -> FileOpen / file_open),
    because addItem needs one. The design stays the source of truth:
    edit it and generate again.
  - The generator is DOM-free (src/ui/designer-codegen.js), with one table
    for the spelling of both languages. generateCode(root, {language,
    name}) gives the whole program; updateCode(existing, root, ...)
    rebuilds the layout section of one already edited and adds only the
    handlers it lacks; saveAsScript(store, ...) is what Save as script
    does. test/designer-codegen.test.js compiles the programs, runs them
    on the in-memory widget host and compares the widgets they build
    with the design.
  - The model - the node tree and its fields - is DOM-free
    (src/ui/designer-model.js, tested in test/designer-model.test.js). A
    node is exactly what the widget host saves (toJson, saveComposite),
    so a composite saved by a program opens in the designer and the
    other way round.


Forum widgets
=============
Made for the Forum window (src/ui/windows/forum-window.js), and usable
anywhere in the IDE. They are not (yet) program widgets.

HtmlPanel
---------
A Panel that shows formatted HTML (a forum post, a preview) and scrolls.
The HTML is sanitized first (src/ui/html-sanitize.js): an allowlist of tags
and attributes; links only http(s) or mailto, opened in a new tab; images
only https or data:image; script, style, forms and frames are removed.
Spoilers open and close when clicked.

  - new HtmlPanel({html, emptyText}); html (get and set), showText(text).
  - CONTENT_STYLE is the look of the content (headings, code, quotes,
    tables) for any element with the class cr-html.

CardListPanel
-------------
A Panel showing a scrolling column of cards, with an optional heading and a
line under it. A card: author with a round avatar (an image, else the first
letter on a colour from the name), a meta line (when), badges, an optional
context line, a body of HTML (sanitized) or text, and action links.

  - new CardListPanel({items, emptyText, heading, subheading}).
  - Items are {value, author, avatar?, meta?, metaTitle?, badges?: [{label,
    tone?}], context?, html? | text?, actions?: [{name, label, tone?}],
    highlight?}; tone is 'warning' or 'danger'.
  - Clicking an action fires action with detail {action, item, index}.
  - replaceItem(value, item), scrollToTop(), scrollToEnd(),
    scrollToItem(value); busy = true greys out every action.

Pager
-----
« ‹ Page 2 of 5 › » for a list read a page at a time. set(page,
totalPages) shows where the list is; choosing another page fires change
with detail {page}. page and totalPages get and set.

CheckBox
--------
A box that is ticked or not, with a label (qooxdoo's CheckBox). new
CheckBox(label, checked); checked, label and enabled get and set; change
fires (detail {checked}) when the user ticks or clears it.

MarkdownEditor
--------------
A Panel for writing a post: formatting buttons (Bold, Italic, Code, Link,
Quote, List, Python code block, Spoiler) that wrap the selection, and Write
/ Preview. The preview is the HTML that previewer, an async function
(text) => html, gives (the forum's server); with none, there is no Preview.

  - new MarkdownEditor({text, placeholder, previewer}); text, placeholder,
    readOnly get and set; mode is 'write' or 'preview'; setMode(mode),
    insert(text), format(how), focus().
  - Ctrl+B, Ctrl+I and Ctrl+K format; Ctrl+Enter fires submit.

ForumWindow, ForumComposeWindow, ForumModerationWindow
------------------------------------------------------
The forum in the IDE (Navbar > Forum). ForumWindow: boards in their groups
(a ListPanel with headings and unread counts) on the left; on the right the
topics (a GridPanel, unread in bold, with search and a Pager) above the
posts of the topic chosen (a CardListPanel with Quote, Edit, Delete,
Approve and Block, as the user may). Buttons: New Topic, Reply,
Follow/Unfollow, Topic (Edit, Pin, Lock, Delete, first/latest post, Open in
Browser), Refresh and, for moderators, Moderation.
ForumComposeWindow writes a new topic, a reply, an edited post or an edited
topic (title; moderators also board, Pinned and Locked).
ForumModerationWindow has Pending, Activity, Users and History tabs.
All of it goes through src/ui/forum-client.js to the server's /forum API
(rails/app/controllers/forum_api_controller.rb and
forum_moderation_controller.rb).
